## What was wrong and what the change does

Reproduced on the base build. [1, 1+2^-52] was written `1 (+/- 1.11e-16)`, which does not reach the upper bound. [0, 5e-324] was `0 (+/- 0)`. [1e308, 1.7e308] was `inf (+/- 3.5e+307)` because l+r overflows. The point interval 0.1 was written `0.1000000000000001`, its center rounded upward. The empty set was `empty` in the width and center formats. intervalToText gave `1.5 (+/- 0.5)` in the width format, `1.25~[0, 67]` in the agreeing format, `[1,25, 1,2567]` under a comma locale, followed the precision, and wrote `<4, 4>`. The header and the manual called the number written the width, but it was half of it.

I made three decisions.

(i) Radius. The width and center formats now write `mid_rad()`: the `midpoint()` and `rad()` of IEEE 1788-2015 12.12.8. Together they enclose the interval, and `rad()` is the smallest radius that does so. The center is written to nearest, the radius upward (`bound_to_text(w, true)`), so a nonzero radius never reads 0. A point interval is written as its center alone. An unbounded interval has radius +oo. I chose to document the two formats as displays rather than make the written text enclose. An enclosing text would need the radius to absorb the rounding of the center's digits. The point interval 0.1 would then read `0.1 (+/- 5.6e-18)`, and [3.452, 3.453] at 2 digits would read `3.5 (+/- 0.049)`. That destroys the stated use of the format, which is to show that an interval is narrower than the digits of its center. The bounds, agreeing and hexa formats stay the enclosing ones. The manual, gaol_interval.h and the comment in operator<< say so, with this reasoning.

(ii) Empty set. `[empty]` is right. IEEE 1788-2015 12.11.3 lists `empty` alone among the non-portable literals and gives `[ ]` and `[empty]` as the portable ones. All five formats now write `[empty]`, and so does the string conversion. The code now matches the manual.

(iii) intervalToText. It is now defined in libgaol, in the `gaol_ieee1788` block of gaol_interval.cpp, next to the existing `pow`. It writes `[l, r]` or `[empty]` in a classic-locale stream with 16 digits, the default precision, through the existing `display_bounds` with a new `angles=false` argument. It is a portable literal whatever the global format, precision and locale. A point interval is `[4, 4]`, because `<a, a>` is no literal of the standard. The manual and doc/accuracy.md are updated. I also fixed the second use of `interval::format()` in operator<<, which read the global twice.

## Behaviour change

Width and center formats: the radius is now rad(), the enclosing radius about the double midpoint, rounded upward. It was (r-l)/2 rounded to nearest. pi prints `3.141592653589793 (+/- 4.440892098500627e-16)` instead of `2.220446049250313e-16`, because the bounds are consecutive doubles and the midpoint is one of them. [0, 5e-324] prints `0 (+/- 4.940656458412466e-324)`. [1, 1+2^-52] prints `1 (+/- 2.220446049250314e-16)`. [1e308, 1.7e308] prints `1.35e+308 (+/- 3.5e+307)`. [-MAX, MAX] prints `0 (+/- 1.797693134862316e+308)` instead of `inf`. A point interval is written as its midpoint to nearest, `0.1` and not `0.1000000000000001`, and interval(-0, 0) is `0` and not `-0`. Because the radius is rounded upward to the digits, [3.452, 3.453] at precision 2 is `3.5 (+/- 0.00051)` and no longer `3.5 (+/- 0.0005)`; I changed the test in tests/input_output.cpp. The empty set is `[empty]` in width and center, and in std::string(I), instead of `empty`. gaol_ieee1788::intervalToText(x) no longer follows the global format, the precision or the locale: it always returns `[l, r]` or `[empty]` with 16 digits and a decimal point, and `[4, 4]` for a point where operator<< writes `<4, 4>`. The default-configuration text of an ordinary interval is unchanged. operator<< in bounds, agreeing and hexa is unchanged.

## API and ABI

No new public name. `gaol_ieee1788::intervalToText(const interval&)` goes from inline to `extern __GAOL_PUBLIC__` and is defined in libgaol, with the same signature. That is a new exported symbol in libgaol, and programs stop inlining the old body; ABI is unchanged for existing callers. The internal `display_bounds` gains a defaulted `bool angles` argument. No installed header is added or removed, and no build file changes.</api_abi>

### 16-correctness-0: approve

Non-blocking remarks:
- Process, not a defect of the change: todo-13-point-interval-text has moved to 704f478 (bound_to_text writes a zero bound to nearest) since this branch was cut from 38d4f20, so `check_branch todo-16-display-formats todo-13-point-interval-text` now fails with 'does not contain'. The branch needs a rebase or merge onto 704f478 before its PR. I merged 704f478 into my detached worktree: it is clean (one hunk in bound_to_text, which the width radius does not reach), and numbers, ieee1788, input_output and rounding_direction pass after the merge. Nothing was committed or pushed.
- gaol/gaol_interval.cpp, operator<<, around l.861: in the center format the code calls I.mid_rad(c, w) and throws w away. midpoint() alone would do for that format and would help point 17.
- gaol/gaol_interval.cpp, around l.862-867: c is written by the stream's own num_put, but w by bound_to_text, which ignores digit grouping. Under a locale with grouping, [1234567, 1234569] gives `1 234 568 (+/- 1)` in fr_FR.utf8. The center was already grouped in the old code, so this is not a regression. The radius used to be grouped too, and the bounds format never groups. Writing c through the same classic-locale path as the bounds would make them consistent.
- With std::showpos the radius reads `+1 (+/- +3e-16)`. The old code did the same, so it is not a regression, but the second sign is odd.
- The center is written `-0` when midpoint() is -0. That happens for tiny subnormal intervals such as [-2^-1073, 2^-1074] and [-2^-1074, 0], which give `-0 (+/- ...)`. It follows midpoint() and is harmless, but it is not the 0 the manual shows for [-0, 0].
- tests/rounding_direction.cpp lists operator<< in the five formats but not gaol_ieee1788::intervalToText, which is now a library function using GAOL_RND_ENTER/LEAVE. I checked by hand that it restores the direction in the GAOL_PRESERVE_ROUNDING build and leaves it upward in the default one, as the other functions do. Adding it to that list would protect this.
- Design point the author already lists in open_questions: intervalToText ignores interval::precision() and always writes 16 digits. This is sound and documented, and the TODO says only 'le format des bornes, avec un point'. It is the maintainer's choice. A user who lowered the precision to shorten intervalToText output now gets 16 digits.


### 16-rules-0: approve

Non-blocking remarks:
- gaol/gaol_ieee1788.h: `#include <sstream>` is no longer used by this header now that intervalToText is out of line. It is harmless and users may rely on it, so removing it is optional.
- tests/numbers.cpp, width_and_center_output(): `hull(random.any(), random.any())` and the `random.uniform(...)` pair rely on unspecified argument evaluation order (pre-existing idiom, also used in arithmetic.cpp). The data therefore differs per compiler: GCC runs 389282 checks and clang-18 388778 on the same source. Nothing fails, but a failure seen on one platform may not reproduce on another. Named locals would make the population identical everywhere.
- tests/numbers.cpp: the center is checked to be within one unit of the last digit (a bound built from |x|*10^(1-p), so up to 10 units for the general format). That does not pin 'rounded to nearest', which is half a unit. The `forms` table (interval(0.1) gives "0.1") is what catches the old rounded-upward center. Tightening the bound to half a unit would be cheap.
- The radius takes the stream flags, so with std::showpos the text reads `+2 (+/- +1)`. The old code did the same and it is now documented nowhere, so it could be left or the sign dropped from the radius. Also, [-5e-324, 0] has a center that is the sign of a tie (`-0 (+/- 4.94e-324)`). This is cosmetic, and `-0` is accepted by the tests.
- The width format under a comma locale is not tested (the locale test only checks bounds and intervalToText). It would print `0,2 (+/- 0,1000000000000001)`, going through the same os.getloc() decimal point as the bounds format.
- At the default 16 digits the upward-rounded radius is visibly noisy for round-looking inputs: [0.1, 0.3] reads `0.2 (+/- 0.1000000000000001)`. That is the documented, intended consequence of never writing a nonzero radius as smaller. A line saying so in the manual next to the [3.452, 3.453] example would help readers.
