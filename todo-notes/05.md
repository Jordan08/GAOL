## What was wrong and what the change does

With -ffinite-math-only (which -ffast-math and -Ofast turn on) the compiler takes NaN and infinities never to occur, in the inline functions of GAOL's headers too, since they are compiled with the options of the program. The empty interval has NaN bounds and is_empty() is !(left() <= right()), so ([1, 2] & [3, 4]).is_empty() was false with GCC 9.4 and Clang 18 (reproduced with a small program against the base commit), and operations on the empty interval gave a NaN interval not told empty; nothing refused the option. gaol/gaol_config.h now has an #error on __FINITE_MATH_ONLY__ (0 or 1 with GCC and Clang, absent with Visual C++, which is untouched) next to the one on __FAST_MATH__. It also closes a hole of the latter that I found: Clang leaves __FAST_MATH__ undefined for -Ofast or -ffast-math followed by -frounding-math but keeps __FINITE_MATH_ONLY__ at 1, so such code compiled silently and gave wrong empty sets. The -fno-fast-math of gaol.pc and gaol::gaol turns the option off only when it comes after it (checked with both compilers), so the refusal is what protects the code otherwise. Two ctest compile tests, refused_finite_math_only and refused_fast_math (tests/refused_options.cpp, tests/CMakeLists.txt), build a program using GAOL with each option, put after the flags of interval arithmetic, in a nested cmake --build, and pass when the message of the header is in the output; they fail without the #error (shown). The options no macro shows are not refused, as the point says (-funsafe-math-optimizations and -ffast-math -fno-finite-math-only with GCC, where the probe 1.0 + tiny == 1.0 is compiled as tiny == 0.0 and width() is below the exact width after a change of the rounding direction; -fno-honor-nans alone with Clang, which I found and which breaks the empty set like -ffinite-math-only): doc/three-builds.md, doc/using.md, the manual and the comment of the header say so, each claim checked on GCC 9.4 and Clang 18. The variants sse, fpu and clang build and pass 47 of 47 tests (2 skipped by design).

## Tests

New tests/refused_options.cpp (a program including <gaol/gaol>, which returns 0 when compiled normally and 1 when compiled past the refusal with -ffinite-math-only, both checked by hand). tests/CMakeLists.txt registers two ctest tests, refused_finite_math_only and refused_fast_math (label unit, RESOURCE_LOCK so that the nested builds never run together, GCC and Clang only, not MSVC/clang-cl). Each test runs `cmake --build <build> --config $<CONFIG> --target gaol_<test>` on an EXCLUDE_FROM_ALL object library made of tests/refused_options.cpp, compiled with the flags gaol::gaol carries (written out from GAOL_INTERVAL_FLAGS and GAOL_FMA_FLAGS, since a linked library's options come after the target's and its -fno-fast-math would cancel the option, checked in flags.make) followed by the option, and passes if the output holds "GAOL cannot be compiled with -ffinite-math-only" (resp. "-ffast-math") (PASS_REGULAR_EXPRESSION on the message, not the exit status, and not just the option name, which Ninja prints in the command line). refused_fast_math covers the existing __FAST_MATH__ check, which had no test. ctest now lists 47 tests (45 + 2); make test runs 31 (label unit). ## Behaviour change

Code that includes GAOL's headers and is compiled with -ffinite-math-only now fails to compile, with a message naming the option and the remedy (-fno-fast-math after it). Before, it compiled and gave wrong results (the empty set no longer told empty). Also refused now: with Clang, -Ofast or -ffast-math followed by -frounding-math (which leaves __FAST_MATH__ undefined but keeps __FINITE_MATH_ONLY__ at 1). No change for code compiled with the flags of gaol.pc or gaol::gaol where -fno-fast-math comes after the user's option (it cancels it, with GCC and Clang), for Visual C++, or for the autotools and meson builds of GAOL itself. IBEX and Codac not checked, as instructed.

## Risks

Code that compiled with -ffinite-math-only (or, with Clang, -Ofast -frounding-math) now fails to compile: intended, it computed wrong empty sets. The new ctest tests run a nested cmake --build inside ctest, on the platforms of the CI that I cannot run: macOS (the Rosetta x86_64 job relies on CMake passing -arch itself, which is why the nested build is used rather than a hand-made compiler command), MinGW and MSYS2 (Ninja, nested ninja checked locally), containers under qemu, Visual Studio (skipped, MSVC true), Xcode generator (not covered); with a make -jN test the nested make may print a jobserver warning (not seen with the CI invocation). The regex looks for the message of the header in the output of the build, so a reworded message needs the tests updated; a compiler that wrapped its diagnostics (-fmessage-length) could split the phrase (the mingw-refused job of windows.yml already greps a message the same way). The tests add about 1 s each to make test.

## For doc/differences.md

- **`-ffinite-math-only`** is refused by `gaol/gaol_config.h`, as `-ffast-math` was. The compiler then takes NaN and infinities never to occur, in the inline functions of the headers too: the empty interval, whose bounds are NaN, was no longer told empty (`([1, 2] & [3, 4]).is_empty()` was false with GCC 9.4 and Clang 18). The CMake tests `refused_finite_math_only` and `refused_fast_math` check the refusal. What no macro shows is not refused and is documented in [Compilers and options refused](three-builds.md#compilers-and-options-refused): `-funsafe-math-optimizations` and `-ffast-math -fno-finite-math-only` with GCC, which compiles the probe `1.0 + tiny == 1.0` as `tiny == 0.0`, so that `width()` is below the exact width after the code using GAOL left the rounding direction to nearest, and `-fno-honor-nans` alone with Clang.

## Reviews

### 5-correctness-0: approve

Non-blocking remarks:
- tests/refused_options.cpp: the bounds are compile-time constants. Past the refusal (base header, -ffinite-math-only, Clang 18 -O2) the program returns 0, because Clang folds the intersection. GCC -O3 returns 1. The report says it returns 1 past the refusal, which is not true for Clang. Volatile doubles, as in the author's repro.cpp, would make the program show the bug with both compilers. The tests only check the refusal message, so this is not blocking.
- The claim '([1, 2] & [3, 4]).is_empty() is false (GCC 9, Clang 18)' appears in gaol/gaol_config.h, doc/three-builds.md, doc/tests.md and tests/refused_options.cpp. It holds for GCC only at -O1 and above (GCC -O0 is correct), and for Clang only when the bounds are not folded at compile time. Something like 'in optimized code, for bounds the compiler cannot fold' would be exact.
- House rule on keeping the three builds alike: the two ctest compile tests exist only in the CMake build. The point itself asks for a test 'comme dans tests/fp_strict', which is CMake-only, and tests/find_package and tests/fetch_content are CMake-only too. The author raised it under open_questions and doc/tests.md says so. The maintainer may still want a shell-script version registered in tests/Makefile.am and tests/meson.build.
- doc/three-builds.md, the new paragraph after the table: 'the code including GAOL's headers is refused when the option follows it' is ambiguous, since 'it' can read as -fno-fast-math. Something like 'when -ffast-math or -ffinite-math-only comes after -fno-fast-math' is clearer. doc/using.md has a similar 'where the compilation stops'.
- The two tests have no positive control, meaning a build of the same object without the option that must succeed. A false pass is impossible, because the regex needs the message. A third ctest test would also protect against a header that refuses everything, but other tests already catch that, so this is optional.
- doc/tests.md: the line beginning 'by the CMake build where the compiler is GCC or Clang. `tests/refused_options.cpp`,' is longer than the surrounding 80-column wrapping.
