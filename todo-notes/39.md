# Point 39: the Goldstein-Price function of the manual forgets the +1

Report of the agent that made the change (written in English, as produced), and the reviews. The branch is `todo-39-goldstein-price`; head at the time: `4ce59b6`.

## What was wrong and what the change does

The diagnosis of point 39 was verified. The overview program of manual/v5/gaol.tex and examples/16_Goldstein_Price.cpp (the GAOL 4 example) both computed (x + y)^2 where the Goldstein-Price function has (x + y + 1)^2. Their enclosure [-56254330, 94177270] is the natural extension of another function: that function is 111 at (0, -1), not 3. The manual said f "ranges over" this interval, whose width is 148 times that of the true range [3, 1015690.2717980589...] (computed with mpmath: minimum 3 at (0, -1), maximum on the edge y = 2 at x = -1.7373725377583070115). The true function's natural extension over [-2, 2]^2 is [-87881320, 147125080], computed by exact rational arithmetic in the order of the expression; it is 231.4 times wider than the range. Every bound met on the way is an integer, the largest being 147125080, far below 2^53, so no operation rounds and the enclosure is the same on every build (checked in SSE2, FPU and Clang). 16_Goldstein_Price.cpp now evaluates the true function through a function goldstein_price(x, y) (the GAOL 4 expression, with +1 added, timing loop unchanged) and, like examples 01 to 15, exits with a failure when a check fails. It checks f(0, -1) = 3, that z encloses [3, 1015690.27...], that z equals [-87881320, 147125080], that the manual's program (sqr, integer constants) gives the same z, that z is 231 times wider than the range, and that [-oo, +oo] * [0] = {0}, which the example printed without checking. The manual's overview chapter now has the +1, the output z = [-87881320, 147125080] (produced by compiling and running the manual's program), and text saying that z encloses the range of f without being it. It gives the true range, the ratio 231, the dependency problem, and points to examples/03_dependency_problem.cpp for subdivision. The comment of example 03, the comment of examples/CMakeLists.txt and examples/examples.md (table, section 16, recommendation 16) were brought in line. The manual compiles with pdflatex (build-pdf.sh, into tmp, PDF not committed) and the output is correct.

## How the test was shown to fail without the fix

I saved the fixed 16_Goldstein_Price.cpp, then reverted only the +1 in goldstein_price() with sed (pow(x+y+interval(1,1),2) became pow(x+y,2)), keeping the checks. I rebuilt with `gcore cmake --build $SCR/build/39-goldstein-price-sse -j1 --target 16_Goldstein_Price` and ran the program and `ctest -R 16_Goldstein`. The program printed z = [-56254330, 94177270] and "FAILED: f(0, -1) = 3", "FAILED: z is the natural extension of f" and "FAILED: z is 231 times wider than the range of f" (it computed 148), exit 1, and ctest reported 0% tests passed (test 45 Failed). I then restored the fixed file, rebuilt, and the example printed z = [-87881320, 147125080] and ctest passed. The check "z encloses the range" passes with the old function too, since [-56254330, 94177270] also contains [3, 1015690.27]; the point evaluation, the exact enclosure and the ratio are the checks with teeth.

## Risks

The check "z equals [-87881320, 147125080]" is a check on digits, which examples.md says the checks never are. It is exact by construction: all bounds are integers below 2^53, so no operation rounds, and it passed in SSE2, FPU and Clang here. The other CI platforms (x87 with extended precision, ARM, s390x, MSVC) were not run, and reasoning says the same. If the maintainer prefers containment checks only, the point evaluation and the ratio would remain and keep the teeth. The ratio check (231 to 232) also depends only on those exact widths. The 1 000 000-evaluation loop is unchanged in work, but goldstein_price() is now a function. Timings before and after were alike (about 200 ms, without contention) with the sse build.
