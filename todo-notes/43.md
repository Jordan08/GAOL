# Point 43: a VERSION.txt that begins with a byte order mark

Report of the agent that made the change (written in English, as produced), and the reviews. The branch is `todo-43-version-bom`; head at the time: `196cfd0`.

## Commits

- 57bf68a The three builds ignore a byte order mark in VERSION.txt, and show the bytes of a refused one
- 196cfd0 Documentation of the byte order mark in VERSION.txt, of the test version_file and of version-file.sh

## What was wrong and what the change does

Point 43 is real and reproduced. On the base commit, a VERSION.txt starting with a UTF-8 byte order mark (EF BB BF) was refused by CMake, meson (0.53.2) and configure with `VERSION.txt holds "5.0.0"`, the mark being invisible. The line ends of Windows (CR LF) alone already worked in all three, and I tested them combined with the mark. CMake's `file(READ)` and `string(STRIP)` keep the mark in the text, meson's Python `open()` reads it as characters (as three cp1252 characters on Windows), and configure's `tr`/`sed` keep it. The correction ignores a leading mark in all three builds, in the way each reads the file. CMake reads the file with a new function `gaol_read_version()` in `cmake/gaol_version.cmake`, included before `project()`; it skips the first three bytes when `file(READ ... LIMIT 3 HEX)` gives `efbbbf`. meson opens the file with `encoding='utf-8-sig'` in the Python one-liner of `project()`. configure and the m4 macro of `configure.ac` remove the mark with `LC_ALL=C sed "1s/^BOM//"`, the bytes being made by `printf '\357\273\277'` because sed has no portable escape for them, and `configure` is regenerated with `AUTOHEADER=true autoreconf`. The error message of the three builds now also gives the first 32 bytes of the file in hexadecimal: `VERSION.txt holds "5.0.x" (bytes in hexadecimal: 35 2e 30 2e 78 0a), where it should hold...`. Writing that message showed that a UTF-16 file (which Windows PowerShell 5 writes for `>`) cut the CMake message at the first NUL byte. So CMake now quotes only the text before the first NUL and refuses any file that holds one; meson writes the text through `ascii()` (one line, escapes). Only a leading mark is removed: a second mark, or one inside the file, is refused with its bytes visible. The regression test is the CTest test `version_file`, a `cmake -P` script that writes VERSION.txt files with and without a mark, with CR LF, and invalid ones, and calls the real function. `.github/scripts/version-file.sh configure|meson` does the same for configure and meson on a copy of the tree, and is run by the autotools job, the meson job and the MSYS2 meson job of `build-systems.yml`.

## Tests

(1) tests/version_file.cmake, registered as the CTest test `version_file` (label unit) in tests/CMakeLists.txt, with two binary fixtures in tests/version_file/ because CMake cannot write a NUL byte. It has 22 checks and calls the real gaol_read_version(). Accepted, expected 5.0.0 (12.345.6789 and 0.0.0 also checked): a line, no line end, mark plus line, mark without line end, CR LF, mark plus CR LF, mark plus empty lines and blanks. Refused, with the exact bytes in the message: mark alone, two marks, mark inside, two numbers, four numbers, leading zero, a letter, a blank inside, two lines, a zero-width space, an empty file, the UTF-16 file (the message must be complete), and 5.0.0 followed by a NUL byte and an x. The test also checks that the mark it writes is really EF BB BF. Expected versions and hexadecimal strings are literals, not read back from the code. It does not depend on file(WRITE) converting LF to CRLF on Windows. It is CMake only, since it tests CMake's code, and tests/Makefile.am and tests/meson.build are unchanged. (2) .github/scripts/version-file.sh configure|meson, 13 cases each (7 accepted, 6 refused). The macros GAOL_VERSION, GAOL_MAJOR_VERSION, GAOL_MINOR_VERSION and GAOL_MICRO_VERSION of gaol/gaol_configuration.h are checked for 7.3.11, a version other than the tree's own, so the value is proven to come from the file. Refused files are checked for the exact hexadecimal bytes in the message.

## Behaviour change

A VERSION.txt that starts with a UTF-8 byte order mark is now accepted by CMake, meson and configure, where the three refused it. CR LF, blanks and empty lines were already accepted and still are. The error message for a refused VERSION.txt now adds '(bytes in hexadecimal: 35 2e 30 ...)', the first 32 bytes of the file, after the quoted text. A file holding a NUL byte (UTF-16) is refused by CMake even if the text before the NUL looks like a version, where the regular expression stopped at the NUL. Nothing changes for GAOL 5.0.0 as it is, since the committed VERSION.txt has no mark.

## Risks

(1) The CI steps could not run here on their real platforms: macOS (BSD sed, od, tr, mktemp, bsdtar) and MSYS2 (Windows Python) are untested. The script is plain POSIX sh, uses LC_ALL=C for sed and grep and printf for the bytes, and passed under dash and Linux; if a CI job fails on version-file.sh, the cause is more likely that platform's tools than the correction. (2) The new MSYS2 step (meson only) runs meson setup on a copy of the tree with MSYS2's Python, where the default encoding may differ; that is the case utf-8-sig protects, but nobody could run it. (3) The minimum-CMake job (3.14) was not run: the functions used (file READ LIMIT HEX, string SUBSTRING -1, REGEX MATCH, LENGTH, function, get_property GLOBAL) all exist in 3.14. (4) tests/version_file/ holds two small binary files, which git stores as binary because of their NUL bytes; a checkout tool that rewrites them would break the two NUL checks. (5) The function gaol_read_version is global in the parent project when GAOL is used with FetchContent; the name is prefixed. (6) The version_file test writes 'VERSION.txt' into the build directory tests/version_file/, not into the tree.

## Open questions and decisions for the maintainer

1. Not fixed, not in this point: the reading rules are not exactly the same everywhere for exotic blanks. The m4 line of configure.ac (`tr -d ' \t\r\n'`) removes blanks inside the text, so autoconf accepts '5. 0.0' at generation time while configure, CMake and meson refuse it when they run; and meson's Python `.strip()` also strips Unicode spaces such as a no-break space at the ends, which CMake refuses (configure depends on the locale). Harmless for a real version; tightening meson to `.strip(' \t\n\r\f\v')` is possible if wanted. 2. Choice made: a UTF-16 file is refused with its bytes shown, not decoded; accepting or hinting UTF-16 ('save the file as UTF-8') is an option, but the point asked for the mark only. 3. Only a leading mark is removed (not one anywhere, as `tr -d` would do), so a file made by concatenating two files with marks is refused, with the bytes shown. 4. I added no Windows-native step (meson-msvc, in pwsh) to build-systems.yml: `sh` from Git for Windows would sit before Visual C++'s `link` on the PATH, which the comment of that job avoids; the MSYS2 meson job runs the script instead. Say if a pwsh step is wanted. 5. Noticed, not mine: gaol.pc.in line 8 still says 'Version is the one configure read from VERSION' (the file is now VERSION.txt, since commit 5335039). 6. CMake gives no test for the NUL cases without the two committed binary fixtures; a text generator (python) in ctest was avoided so that no interpreter is needed.

Blocking:
- The CTest test `version_file` FAILS on CMake 3.14.7, the minimum CMake that CI runs (.github/workflows/linux.yml, job `cmake-3-14`, which runs `cmake --build build --target test`). I reproduced it: I configured the branch with the CMake 3.14.7 binary from Kitware (kept in scratchpad/tmp/29-ci-comma-locale/cmake314) and ran `ctest -R version_file`. CMake 3.14 to 3.16 treats an empty match of `string(REGEX MATCH)` as a fatal error. That happens whenever the text left after removing the mark is empty, that is for a VERSION.txt holding only a mark or holding nothing (cases 'a mark alone' and 'an empty file'). Consequence beyond the test: with those CMake versions, a mark-only or empty VERSION.txt gives this cryptic error instead of the message with the hexadecimal bytes that the point promises. The author's report said the 3.14 job was not run because 'the functions used all exist in 3.14', but their behaviour differs.
- The guard against a NUL byte does not work on CMake 3.14.7 and 3.16.3, and the test `version_file` checks it ('a NUL byte after the version'). On those versions `file(READ)` cuts the text at the first NUL byte: I measured `string(LENGTH)` = 5 for the 7-byte fixture tests/version_file/nul_after_version.txt (`35 2e 30 2e 30 00 78`), where CMake 4.4.3 gives 7. So `_length EQUAL _shown_length` is always true there and the file is accepted as "5.0.0". After I fixed the empty-match error on a copy, 3.14.7 and 3.16.3 still failed with `a NUL byte after the version: accepted as "5.0.0"` (1 of 22 checks). So `version_file` stays red on the minimum-CMake job. The claim in doc/tests.md ('a NUL byte after `5.0.0` has to make the file refused') and in the comment of cmake/gaol_version.cmake ('file(READ) keeps a NUL byte in the text') is only true for recent CMake. The rule 'refuse a file holding a NUL byte' therefore depends on the CMake version, and meson and configure do not follow it either (see nits).
