## What was wrong and what the change does

operator>> (gaol/gaol_interval.cpp) read the rest of the current line with std::getline(is, buffer). Where the previous value had stopped just before a line end, it read the empty text "" and threw input_format_error. So `in >> d >> x` over "1.5\n[1, 2]\n" threw, and `while (in >> x)` over a file ending with an empty line (or with a blank line between two intervals) ended with an exception; I reproduced all of it on the base commit. The fix is the one the point proposes: `std::getline(is >> std::ws, buffer)`. std::ws skips the blanks and line ends before the line, as the reading of a double does, and it does so whatever std::noskipws says, because it is an explicit unformatted skip and not a sentry. A blank line, or a line of blanks or CRLF ends, is therefore skipped like a blank between two numbers. At the end of the input ws sets eofbit and getline then sets failbit: no exception, the interval unchanged, exactly as for a double (I checked that a double leaves its value untouched and gets eof|fail in the same situations). An ill-formed line still sets failbit and throws input_format_error (invalid_action_error where the reader raises it); an interval spread over two lines is still refused, because the reader remains line-based. I chose the code fix rather than documenting that an empty line is ill-formed, since it is the option that fits IEEE-style stream idioms and the maintainer's own preference. The word-based reader was not done (see open_questions). I added a Doxygen comment to operator>> in gaol_interval.h and updated the manual entry and doc/tests.md.

## Behaviour change

operator>> now skips the blanks, line ends included, before the line it reads. Blank lines and lines of blanks (also with CRLF ends) are no longer read as the empty text: "[1, 2]\n[3, 4]\n\n" gives 2 intervals with no exception (while (in >> x) ends with failbit|eofbit); "[1, 2]\n\n[3, 4]\n" gives both intervals; `in >> d >> x` over "1.5\n[1, 2]\n" reads d = 1.5 and x = [1, 2]; over "1.5\n" it reads d, then failbit, x unchanged, nothing thrown (it threw input_format_error and emptied x). A stream holding only blank lines behaves like an empty stream. Unchanged: a line that is no interval sets failbit, empties I and throws input_format_error; an interval written on several lines is refused ("[1,\n2]" fails on "[1,"); well-formed input is read the same with or without std::noskipws. The error message of a refused line no longer shows the blanks that preceded it.

## Risks

Low. One added std::ws before the getline; on well-formed input the only difference is that blanks and line ends before the line are consumed first, which the parser skipped anyway (its SPACE rule is [ \t\r\n]+). Behaviour that changes on purpose: blank lines no longer throw (a program that relied on the exception to detect an empty line will now see them skipped, and a program that depended on `in >> x` failing on an empty line to stop a loop will read on to the next interval or to the end). Interactive input (std::cin) now waits for a non-blank line instead of failing on a bare Enter, as for numbers. Portability: std::ws and std::getline behave the same in libstdc++, libc++ and the MSVC STL for these cases (ws sets eofbit at the end and getline's sentry then sets failbit; std::noskipws does not affect std::ws); the CI platforms I cannot run (macOS, Windows, s390x, musl, ...) use these standard facilities only. The stream tests compare with the behaviour of double on the same platform rather than hard-coding library-specific state bits, and a locale is not involved.

## Open questions and decisions for the maintainer

1. Word-based reading (to re-read `os << x << ' ' << y`) was NOT done: intervals contain spaces ("[1, 2]"), and the grammar allows nested literals and full expressions ("[[1, 2], 3]", "sqrt(2)+1", "1 -2"), so where an interval ends in a stream is ambiguous; a clean rule would need to match brackets for literals and refuse or restrict expressions, which changes what operator>> accepts. Options for the maintainer: (a) keep one interval per line (documented; what I did); (b) accept only interval literals ("[..]", "<..>", "empty", numbers) read up to the matching bracket, keeping the line reader for the rest; (c) a separate function. It needs a decision on the accepted syntax before any code. Writing with a newline (`os << x << '\n' << y`) round-trips today. 2. Corner case: on a stream with exceptions(eofbit) only, an interval read at the end of the input now throws from std::ws with the state eofbit alone (it used to be eofbit|failbit, set by getline); a double sets both. An exception is thrown either way, so `while (in >> x)` ends the same; I did not add code for it. Related and pre-existing: with exceptions(eofbit), a last line with no final newline makes getline set eofbit and throw before the line is parsed, as a double throws after reading "1.5" at EOF. 3. On libstdc++ 9 (GCC 9.4) std::ws does not check good() first, so on a stream already in fail state it still consumes the blanks (other library versions do not); this is invisible, since those blanks would be skipped by the next read anyway, and the test only requires that nothing is read or thrown and that reading resumes after clear(). 4. A '\v' or '\f' before a line is skipped by std::ws (isspace) though the lexer does not treat them as blanks: harmless, they are leading blanks either way. 5. Other things noticed, not fixed: after an exception from getline/ws with exceptions(failbit), the ios_base::failure propagates unchanged (consistent with double); the manual's existing text says "if the library was compiled with exceptions enabled ... prints an error message to cerr and aborts", untouched. No other bug found.

## Reviews

### 15-correctness-0: changes

Blocking:
- std::ws runs before any sentry. In libstdc++ 9 and 10 (/usr/include/c++/9/bits/istream.tcc:1024-1043, identical in 10) it does not check good() and does not flush is.tie(). I measured three regressions against the base, one of them a crash. (a) `std::istream in(nullptr); interval x(1.0, 2.0); in >> x;` gives SIGSEGV (exit 139) with the branch, because ws calls rdbuf()->sgetc() on a null pointer. The base sets failbit|badbit and returns, as `in >> d` does for a double. (b) On a stream that is not good, ws still consumes characters. Over "\n\n[1, 2]\nrest\n", after setstate(failbit), `in >> x`, `in.clear()`, `std::getline(in, s)`, s is "[1, 2]" with the branch and "" on the base; the same holds for badbit. So the test "operator>> on a stream in failbit state reads nothing" passes only because the consumed blank would be skipped anyway. (c) A tied stream is no longer flushed before the first read of the input. With a streambuf logging sync() and underflow(), the flush comes first for a double, for the base interval and for the guard variant `if (is.good()) is >> std::ws;`, and only after the first underflow with the branch. So `std::ios::sync_with_stdio(false); std::cout << "x = "; std::cin >> x;` shows its prompt only after the user has typed. The author's report says std::ws behaves the same in libstdc++, libc++ and MSVC for these cases; that is false for libstdc++ (the report's own open_questions item 3 saw (b) and dismissed it).

Non-blocking remarks:
- doc/tests.md l.132-138: "end of the input as `while (in >> d)` does over numbers, whatever the `exceptions()` of the stream" claims too much. I compared `while (in >> x)` and `while (in >> d)` over 4000 random texts (blank lines, CRLF, blanks, no final newline) for all 8 masks of eofbit|failbit|badbit. Without eofbit in the mask (32000 loops), values, exception type, failbit and eofbit are identical. With eofbit in the mask, 28600 of 32000 loops differ: std::ws throws with eofbit alone where a double gets eofbit|failbit, and a last line without a line end throws from getline before it is parsed (that second part predates the branch). Say "with failbit and badbit in exceptions()", or mention that eofbit is not covered. The author's open_questions item 2 already knows this.
- doc/tests.md l.132: "skipped, as the blanks before a number are, with or without `std::noskipws`" can be read as saying that numbers skip blanks under noskipws, which they do not. Rewrite it as "blank lines have to be skipped, with or without std::noskipws, which stops the blanks before a number but not the reading of a line".
- manual/v5/gaol.tex l.3141-3147: "...is not a line to read, whether std::noskipws is set or not, and an interval cannot be written on several lines" chains two unrelated ideas in one sentence. Put "An interval cannot be written on several lines" in a sentence of its own. The generated PDF renders correctly, so this is style only.
- gaol/gaol_interval.h, Doxygen comment of operator>>: unlike the manual, it does not say that with exceptions disabled a refused line prints to cerr and aborts. Optional.
- examples/examples.md l.62-63, l.447-450 and row 14 of section 5.2 (l.622) still say that a blank line throws input_format_error. The author reported them for the orchestrator; make sure the bookkeeping pull request corrects them.
- Not blocking: the null-rdbuf test named in the blocking item would be the first check in this test program whose failure is a crash and not a FAILED line. Put it in a stream_input() block of its own, run last, with a comment saying why.
