# Point 6: pow misses a subnormal result when the x87 unit and MXCSR disagree

Report of the agent that made the change (written in English, as produced), and the reviews. The branch is `todo-06-fegetround-mxcsr`; head at the time: `93fdc4f`.

## Commits

- 1d97bab CORE-MATH's fegetround() reads MXCSR on x86-64: pow missed a subnormal result with the x87 unit to nearest
- 93fdc4f Document fegetround() read from MXCSR in 3rd/README.md and pow with a subnormal result in doc/tests.md

## What was wrong and what the change does

On x86-64 with glibc, pow with a subnormal result missed the exact value when the x87 unit rounded to nearest and MXCSR upward. That is the state left by exactinit() of the predicates of Shewchuk and of Triangle. CORE-MATH's pow (pow.h, lines 236, 261 and 408) rounds such results itself, in the direction fegetround() gives, and glibc's fegetround() reads only the x87 control word. GAOL's probe (1 + 2^-60 > 1) sees MXCSR only and so leaves the x87 unit alone. pow then rounded to nearest, so the upper bound was below the exact value. I reproduced it: 182 of 400 random subnormal-result cases did not enclose in that state (the review's sample gave 205), and none did in the other five states. The reference was mpmath at 600 bits. The fix is in gaol/core_math_port.h, which the three builds force-include into every CORE-MATH source only. On x86-64 (`__x86_64__` or `_M_X64`), after including <fenv.h> and <xmmintrin.h>, it defines a static inline gaol_fegetround() that reads MXCSR and maps its RC field to FE_TONEAREST, FE_DOWNWARD, FE_UPWARD or FE_TOWARDZERO through a switch. It then does `#undef fegetround` and `#define fegetround gaol_fegetround`. The switch keeps it independent of the FE_* values of each C library (Windows differs from glibc). The #undef covers a libc where fegetround is a macro, and the redefinition comes after <fenv.h> is fully included, so no declaration is rewritten. The vendored sources are unchanged, and the C++ code of GAOL never sees the macro. After the fix pow.o, cos.o and tan.o have no fegetround reference and use stmxcsr. I chose x86-64 only. On i386 GAOL already reads fegetround() and MXCSR in round_upward_if_needed() and sets both units when either is not upward, so the two never differ when CORE-MATH runs, and the code there cannot be tested here. Extending the guard would only add defence in depth, and would make the gaol_fpu.h comments about 32-bit x86 stale.

## Tests

tests/rounding_direction.cpp gets an array subnormal_powers[]: three x^y with results of 1458662373659.29, 567863.26 and 1.30 times 2^-1074. The first is the case of Appendix B item 3, the other two are new. Their tightest enclosures are written as multiples of 2^-1074, computed apart with mpmath. The exact values have a fractional part below one half, so rounding to nearest gives a value below the exact one. Two checks use it. First, a new entry "gaol_ieee1788::pow with a subnormal result" in the operations list: the differential check against the upward result in the 6 states, the direction left unchanged or upward, and the [a]*[b] and [a]+[b] tightness afterwards. Second, a block before the cleanup section that compares pow with the mpmath enclosures in each of the 6 states ("the tightest enclosure", 18 checks). The header comment of the test is updated. I did not keep a fourth case, a deep underflow to [0, 2^-1074]: CORE-MATH rounds it by hardware, so it did not exercise the fix.

## How the test was shown to fail without the fix

Only gaol/core_math_port.h was put back to HEAD (`git show HEAD:gaol/core_math_port.h > gaol/core_math_port.h`), with the new test kept. I rebuilt gaol_test_rounding_direction in build/06-fegetround-mxcsr-sse and ran it. It exited 1 with "16934 checks, 9 failed". Six checks failed among the 36 of "gaol_ieee1788::pow with a subnormal result: the same result whatever the rounding direction", and three among the 18 of "...: the tightest enclosure". All nine are in the state "to nearest, and upward for SSE", so the "6 checks" of Appendix B is reproduced. For example, the upper bound was 0x0.001539f0d791bp-1022 rather than ...c. With the fix restored and rebuilt, the same test gives "16934 checks, 0 failed". A standalone program (scratchpad tmp/06-fegetround-mxcsr/repro.cpp) had shown 182 of 400 cases failing in that state before the fix and 0 after.

## Behaviour change

On x86-64, gaol_ieee1788::pow(I, J) (and nth_root through pow) with a subnormal result now encloses the exact value whatever the x87 unit says. Before, with the x87 unit to nearest and MXCSR upward, about half of the subnormal results had an upper bound below the exact value. Nothing changes when both units agree, where the bounds are bit-identical to before, nor on other architectures. The same code in cos and tan is also read from MXCSR now, with no observable case.

## API and ABI

none. core_math_port.h is not installed. gaol_fegetround() is static, and the fegetround macro exists only in the CORE-MATH translation units. No exported symbol, header or installed file changes.

## Risks

Low. The change only touches the C sources of CORE-MATH, and only where the x87 unit and MXCSR differ; when they agree, the direction read is the same as before. The SSE unit computes the doubles of CORE-MATH, so it is the right unit to read. The mapping goes through the FE_* constants of each libc, not through numeric values. The redefinition is placed after <fenv.h> and after the includes of the port header, so no declaration is rewritten, and it is object-like so that `#undef fegetround` also covers a libc making it a macro. It is untested on macOS x86_64, musl, MinGW x64 and MSVC x64, which only CI can check. On MSVC x64 it relies on _mm_getcsr, _MM_ROUND_MASK and their siblings from <xmmintrin.h>, which GAOL already uses there.

## Open questions and decisions for the maintainer

1. Refusal of MinGW-w64 before version 12 on x64 (gaol/gaol_config.h, doc/three-builds.md, doc/continuous-integration.md, manual/v5/gaol.tex, doc/differences.md, four jobs of windows.yml). It rests on "CORE-MATH reads fegetround() to know the direction GAOL set by writing the registers". After this change that no longer applies on x64, where CORE-MATH's fegetround() is read from MXCSR. I did not lift it: no such MinGW is available here, and CI would have to show that those compilers then pass. On 32-bit x86 the reason is unchanged. It is a maintainer decision. 2. i386 with __SSE2_MATH__: I left it out (see summary). The alternative is to extend the guard to `(defined(__i386__) && defined(__SSE2_MATH__))`, and MSVC x86 with /arch:SSE2. That would also let round_upward_if_needed() of gaol_fpu.h drop its x87 check on 32-bit x86, but I could not test any of it, and CI has i386 jobs. 3. Platforms I could not check. macOS x86_64: I do not know whether Apple's fegetround() already reads MXCSR. musl on x86-64: I believe its fegetround() reads MXCSR. I could not verify this offline, and defining it as an MXCSR read gives the same answer where it already does. MSVC x64 and MinGW x64: not built here; CI covers them. The test needs nothing from those platforms, because the tightest enclosures are the same on every platform. 4. Upstream (point 31): the vendored pow.h, cos.c and tan.c depend on fegetround() the same way, so any libc that reads only the x87 unit on x86-64 has the disagreement. It is worth reporting to CORE-MATH, with the reproduction. I sent nothing. 5. Noticed, not fixed: the comment of round_upward_if_needed() in gaol/gaol_fpu.h says "The C library computes in the direction GAOL sets before calling it (round_nearest()), whatever the x87 unit had". GAOL no longer switches to nearest for the elementary functions, so that sentence is stale. The branch of pow.h:236 with ex >= 64 (result at or below 2^-1075) differs between nearest and upward only at an exact tie, and I found no argument reaching it, since pow.c handles the deep underflow by hardware. The qint path (pow.h:408) is unreachable by any input I tried; it is covered by the same redefinition.
