## What was wrong and what the change does

With denormals-are-zero (DAZ) set in MXCSR, which a program linked with -Ofast gets from crtfastmath.o and code it loads can set, the reader read every subnormal double as 0: gaol_compare_number() (gaol/gaol_interval_lexer.lpp) tested x < 0.0, x > 0.0 and x > DBL_MAX on the candidate double and took std::frexp() of it, and DAZ makes those comparisons and glibc's frexp (which multiplies a subnormal by 2^54) see 0. Every subnormal thus compared below the number read, so textToInterval("1e-310") was [0x0.fffffffffffffp-1022, 0x1p-1022], which does not contain it, as the TODO says; I reproduced it, and also with a real program linked with -Ofast (MXCSR 0xdfc0 at main). The diagnosis was incomplete for the worst case: with v = 0 the comparison answered "equal" for every subnormal, so textToInterval("0") was the point interval at the greatest subnormal 0x0.fffffffffffffp-1022, not 0. FTZ alone changes nothing, the reader computing no subnormal result. The correction takes the candidate apart by its bits, as the bisection already did: zero, positive (0 < x <= +oo, the bits of a negative number or a NaN being above those of +oo) and +oo are decided on the bits, and M and e come from the fraction and the biased exponent (M gets 2^52 and e = biased - 1075 for a normal double, e = -1074 for a subnormal, so M is no longer normalized to 53 bits). The high 32-bit digit of the natural number B is therefore pushed only when it is not zero, because gaol_natural_compare() compares sizes first and needs no leading zero digit; gaol_bits_of() and gaol_double_of() moved above the function. gaol_interval_lexer.cpp was regenerated with `cmake --build <build> --target parser` (flex 2.6.4, bison 3.5.1): the parser files are unchanged, the .cpp diff is the .lpp change plus #line shifts, and a fresh regeneration from the committed sources is byte-identical. The interval writer shares the function (gaol::compare_number_with_double) and gets the same repair. The new test in tests/numbers.cpp sets FTZ/DAZ around textToInterval only (RAII, x86, skipped with a message otherwise) and compares with the exact arithmetic of gaol_tests.h.

## Behaviour change

Only with denormals-are-zero set (programs linked with -Ofast, code loaded by them): textToInterval("0") is [0, 0] instead of the point at the greatest subnormal 0x0.fffffffffffffp-1022, and every number from 0 to the least normal double is read as the tightest enclosure instead of [0x0.fffffffffffffp-1022, 0x1p-1022] or that point (so also the bounds of interval literals and of the uncertain form, and the decimal output that shares the comparison). Nothing changes in the other cases: same bounds on 100014 random texts, with and without FTZ/DAZ. FTZ alone was never affected.

## Risks

Low for the library: bounds are bit-identical wherever the old code was right (see the differential check and the 72k existing checks). The only semantic difference of gaol_compare_number() outside the bug is a NaN candidate with v = 0, which now gives 1 instead of 0; no caller passes a NaN (candidates are gaol_double_of() of bits up to those of +oo, and fabs() of finite nonzero bounds in the writer). The subnormal M is no longer normalized, which the "no leading zero digit" condition of gaol_natural_compare() required me to handle (B gets its high digit only when non zero); covered by the tests and by the differential check. For the test: it sets DAZ, which every x86-64 processor supports (setting an unsupported MXCSR bit would fault); it restores the bits by RAII even if textToInterval throws; it skips at run time when DAZ is not honoured (emulators) and compiles to a message elsewhere. The new lines were compiled with GCC 9.4 and Clang 18 only: the MSVC and macOS builds are not tested here (local struct in a vector initializer list, hexadecimal float literals already used in the file, xmmintrin.h as gaol_fpu.h includes it).

## Open questions and decisions for the maintainer

1. The same DAZ effect exists outside the reader, in code that compares subnormal doubles as doubles (I checked by experiment with the fixed library, DAZ set, and did not fix them, being out of point 11): (a) the literal <a, b> is accepted with two different subnormal bounds, because the action of gaol_interval_parser.ypp tests l.left() != r.right() as doubles (<1e-310, 1e-309> and <0x1p-1074, 0x1p-1073> throw normally, give [1e-310-, 1e-309+] and [2^-1074, 2^-1073] under DAZ); fixing it means editing the .ypp and regenerating the parser files; (b) operator<< writes [0, 5e-324] as <0, 4.95e-324> (the "degenerate interval" form) under DAZ, because the two bounds compare equal, and a subnormal bound goes through the C library path of bound_to_text() (x == 0.0), so its enclosure then depends on the C library's rounding; (c) the constructor interval(l, r) does not turn subnormal bounds in the wrong order into the empty set ([0x1p-1073, 0x1p-1074] keeps reversed bounds instead of NaN), its l <= r being flushed. This belongs to the spirit of point 4: its cure (clear FTZ/DAZ when the probe of round_upward_if_needed() sees them) only protects the entries that run that probe, and the reader, the writer and the <a, b> check run none for a plain number, so one decision is needed: make them mode-independent as the reader is now, or have them run the probe. 2. The AArch64 and ARM32 processors have the same flush mode (FPCR.FZ, flushing inputs and results) and the old reader was wrong there too; the fix is generic, but the test is skipped there (arm64 macOS, Windows and the Linux containers of the CI), because setting FPCR needs inline assembly (GCC, Clang) or _WriteStatusReg (MSVC) that I cannot run here. Add it? 3. Alternative not chosen: clear FTZ/DAZ in MXCSR around the reader (as point 4 proposes for operations), with a save and restore; the bit-based comparison needs no mode change, works on ARM and is faster, so I kept it; the TODO asked for it. 4. The new manual sentence carries the [GAOL v5] mark without saying what GAOL 4 did: GAOL 4 (strtod with directed rounding) was not tested under DAZ; the maintainer may prefer to drop the mark or test GAOL_V1.
