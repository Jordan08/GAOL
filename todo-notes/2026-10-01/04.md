## What was wrong and what the change does

With the flush-to-zero (FTZ) / denormals-are-zero (DAZ) modes of x86, or FZ of ARM, every operation with a subnormal operand or
result loses its enclosure (`[1e-300]*[1e-20]` = [0, 0]). A program linked with `-Ofast`, `-ffast-math` or
`-funsafe-math-optimizations` gets them from `crtfastmath.o` (GCC and Clang, on x86 Linux/MinGW and on ARM Linux); a shared
library built with `-Ofast` by Clang 18 (or GCC < 13) sets them when it is loaded (`dlopen` of such a `.so` took MXCSR from
0x1f80 to 0x9fc0 here). The probe of each operation saw only the rounding direction.

1. `gaol/gaol_fpu.h`: `GAOL_RND_FLUSH_BITS` (x86 MXCSR 0x8040; AArch64 FPCR FZ|FIZ 0x1000001 with GCC/Clang; ARM32 FPSCR FZ
   0x1000000 with GCC and a VFP), `get_flush_modes()`, `set_flush_modes()`, `clear_flush_to_zero()` (inline asm
   `mrs/msr fpcr`, `vmrs/vmsr fpscr` on ARM), `set_rounding_and_flush_modes()`; the probe `1.0 + (subnormal + 0.0) == 1.0`
   with 2^-1060 wherever the modes can be cleared, which then clears them before `round_upward()`. `GAOL_PRESERVE_ROUNDING`
   saves and restores the modes (one read of MXCSR on x86, Rosetta 2 being slow on it).
2. `gaol/gaol_interval_fpu.cpp`: `*=`, `/=`, `%=` (interval) and `*=`, `/=`, `%=` (double) make their one check before they
   compare the bounds (one `GAOL_RND_ENTER()` at the top, `GAOL_RND_LEAVE()` at each exit; the inner checks are gone, which
   also removes repeated checks, cf. point 2). `gaol/gaol_interval_sse.cpp`: the same for the three operations with a double.
   `gaol/gaol_interval.cpp`: `exp()` takes `maximum(0, u)` before `GAOL_RND_LEAVE()`.
3. `-mno-daz-ftz`: checked by a link in the three builds (as the WIP did); CMake gives it to `gaol::gaol` consumers built by
   the compiler that built GAOL, of its version or later (`$<AND:$<CXX_COMPILER_ID:…>,$<VERSION_GREATER_EQUAL:…>>`,
   verified with an install: GCC consumer gets it, Clang 18 consumer does not and links); `gaol.pc` Libs as asked by the TODO;
   the tests of the three builds are linked with it. GCC releases that have it, read in `gcc/config/i386/i386.opt` of the release
   tags: 11.4, 11.5, 12.4, 13.1 and later (11.3, 12.2, 12.3 do not); the specs of 13.1 (`gnu-user-common.h`, `mingw32.h`) honour it.
4. `tests/fast_math_link.cpp` (new, three builds): linked with `-ffast-math`; where the build gives `-mno-daz-ftz`
   (`GAOL_TESTS_NO_DAZ_FTZ`), the modes must be clear at `main()`; otherwise the first operation must clear those the link set,
   or the test sets them (plug-in case); bounds tightest, modes cleared (restored with PRESERVE).
5. Docs: `doc/using.md`, `doc/three-builds.md`, `doc/tests.md`, `manual/v5/gaol.tex`, header comments (`gaol_fpu.h`,
   `gaol_config.h` for `-fno-signed-zeros`, `gaolConfig.cmake.in`).

## Behaviour change

- Each operation clears the flush modes it finds (x86, ARM with GCC/Clang), and leaves them cleared (restores them with
  `GAOL_PRESERVE_ROUNDING`): a program that wants FTZ/DAZ for its own code loses them after GAOL's first operation.
- Programs linked through `gaol::gaol`/`gaol.pc` by GCC ≥ 11.4/12.4/13 on x86 get `-mno-daz-ftz`: linked with `-Ofast`, their own
  code no longer runs with FTZ/DAZ.
- The probe raises, on x86, the denormal-operand flag of MXCSR (not in `FE_ALL_EXCEPT`); no underflow flag.
- `gaol.pc` from a GAOL built by GCC 13 makes a Clang 18 (or GCC < 11.4) link fail on `-mno-daz-ftz` (documented).

## API and ABI

New inline functions in `gaol_core` (`get_flush_modes`, `set_flush_modes`, `clear_flush_to_zero`,
`set_rounding_and_flush_modes`), macros `GAOL_RND_FLUSH_BITS`, `GAOL_RND_FPCR_REGISTER`, `GAOL_RND_FPSCR_REGISTER`;
`gaol_core::rounding_state` gains a member `flush` on x86 and ARM (inline struct used within one operation). No exported
symbol removed; no change of the class `interval`.

## Risks

- ARM inline asm is compiled and run here only with GCC 13 (cross, qemu) and compiled with clang-18 for aarch64 (link test);
  Apple clang (macOS arm64), MSVC ARM64 (excluded by `__GNUC__`), clang-cl (excluded) rely on the CI.
- If a processor or emulator keeps the flush bits without honouring them, GAOL's probe does not clear them (harmless for the
  bounds); the tests skip such modes.
- Comparisons after `GAOL_RND_ENTER()` could in principle be scheduled before the MXCSR/FPCR write by a compiler that does not
  model it (as GCC with the rounding direction); none seen at -O0/-O3 with GCC 13 and Clang 18.
- `gaol.pc` with a different compiler (see open questions).
