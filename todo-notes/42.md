# Point 42: meson 0.53 on Windows can take the fake Python of the Microsoft Store

Report of the agent that made the change (written in English, as produced), and the reviews. The branch is `todo-42-meson-windows-python`; head at the time: `c519a55`.

## Commits

- c519a55 Document meson and the Microsoft Store Python aliases; say why meson.build looks for python3 first

## What was wrong and what the change does

The point's premise is only partly true, and its first suggested correction is not safe. I read the meson sources (0.49 to 1.4 downloaded with pip, plus the installed 0.53.2). meson 0.53.0 and earlier do not discard the Microsoft Store stubs. meson 0.53.1 and later, including the 0.53.2 of Ubuntu 20.04 and the meson of pip, drop %USERPROFILE%\AppData\Local\Microsoft\WindowsApps from the PATH they search (ExternalProgram._windows_sanitize_path, in dependencies/base.py of 0.53.1 and 0.53.2 and in programs.py of 1.x). So the failure can only happen with meson 0.53.0 or older, or when the profile directory is not the one in USERPROFILE. Swapping the arguments to find_program('python', 'python3') on Windows would make things worse. In find_program_impl, all versions from 0.50 to 1.4 fall back on the Python that runs meson (mesonlib.python_command, which is meson.exe runpython for the MSI installer) only when args[0].endswith('python3'). With python first, a Windows machine with no Python on PATH (MSI meson.exe alone) would stop at "Program(s) ['python', 'python3'] not found". Also, WindowsApps holds a python.exe alias as well as python3.exe, so putting python first does not avoid the stub unless a real python.exe comes earlier in PATH. I therefore took the point's second alternative: I documented the behaviour in doc/building.md (the meson section, with a pointer from the VERSION.txt list) and in manual/v5/gaol.tex, and I added a comment in meson.build saying why python3 stays first. meson.build has no code change. I reproduced the mechanism on Linux with stub interpreters that fail the way the Store aliases do (Windows itself was not available). The stub run stopped meson setup on run_command, and the matrix below shows the reorder gains almost nothing and loses the fallback.

## How the test was shown to fail without the fix

Not applicable, since there is no fix in code to revert. To check the reasoning I ran meson 0.53.2 setup (gcore python3 /usr/bin/meson setup) on Linux with a PATH made of a symlink farm without any Python, plus stub scripts that print the Store message and exit 49, standing in for the WindowsApps aliases. The reorder was applied unconditionally for the test. Results, current order (python3, python) against reordered (python, python3): real python3 only gives OK / OK. Stub python3 alone before a real python gives FAIL (run_command status 49) / OK. Stub python3 and stub python before a real python3 gives FAIL / FAIL. No Python at all gives OK (Program python3 NO, python NO, Project version 5.0.0, meson's own Python is used) / FAIL (Program(s) ['python', 'python3'] not found or not executable). With the final tree (comment only), meson setup gives Project version 5.0.0 with the default PATH and with no Python on PATH.
