## Behaviour change

Library users: none (no code, header, option, installed file or ABI change). Whoever builds GAOL with CMake as the top-level project: a CMake Warning (never an error) is printed while configuring when the committed configure was generated for another version than VERSION.txt holds; nothing is printed when they agree or when there is no configure. On Unix hosts building natively, ctest and make test run one more test, cpack_stale_configure.

## Open questions and decisions for the maintainer

1. check_branch reports "FAIL: build products or logs are committed" on this branch, only for doc/building.md: its regex (^|/)(build[^/]*|...)(/|$) matches the path component "building.md" (a tracked documentation file that exists at the base commit). Every point that documents in doc/building.md will get the same false failure; the regex could be build[^/.]* or name the directories. Everything else check_branch tests passes (messages, forbidden files, whitespace). I did not touch the helper. 2. With the Makefile generators, cmake --build <build> --target package_source does not re-run CMake after a change of VERSION.txt (Ninja does, through CMAKE_CONFIGURE_DEPENDS): the archive is then named after the old version and holds the new VERSION.txt (observed: gaol-5.0.0.tar.gz holding VERSION.txt 5.0.2), and the warning shows only when CMake configures. I documented it (configure the build directory again first); a check at CPack time would need CPACK_PRE_BUILD_SCRIPTS (CMake 3.19, the minimum is 3.14) or a dependency of package_source on a re-configuration: the TODO asks for a configure-time message(WARNING), so I stopped there. 3. Automated check: I chose a CTest that configures copies of the tree (the orchestrator's suggestion) rather than a CI step in a workflow (the repo's habit for configure messages, e.g. linux.yml greps configure.log). It costs about 2 to 9 s natively (one full configuration, 3.3 s here, and four that reuse the cache); from the 34.5 s configuration measured in the riscv64 QEMU job of run 36381611526, about 50 s under QEMU. It is registered only on Unix hosts, not cross-compiling, where the tree has a configure, so Windows and MSYS2 jobs do not run it. The maintainer may prefer a single CI step instead. 4. The test asks configure itself for its version (sh configure --version, the CI's own comparison) and does not check that the real tree is consistent: the autotools job of the CI already does. No other bug noticed.

## For doc/differences.md

- **CMake warns of a `configure` generated for another version**: the archive of the sources holds `configure` as it is committed, and `configure --version` gives the version autoconf read from `VERSION.txt` when it generated it (the line `PACKAGE_VERSION=`). After a change of `VERSION.txt` without a new generation of `configure`, the archive of the new version held a `configure` that said the old one, which only the autotools job of the continuous integration reported. CMake now warns while it configures GAOL as the project built, naming both versions, and says nothing without `configure` or without that line; `tests/cpack_stale_configure.cmake` checks it (see [Building GAOL](building.md#the-version-of-gaol)).
