# Point 24: floating-point flags and exceptions

Report of the agent that made the change (written in English, as produced), and the reviews. The branch is `todo-24-fp-exceptions`; head at the time: `79f0632`.

## Commits

## What was wrong and what the change does

With the invalid-operation exception enabled (feenableexcept(FE_INVALID) on glibc), every is_empty() of a computed empty set died on SIGFPE, and so did the operations that start with that test: is_empty() compared the NaN bounds of the empty set with <=, a signaling comparison (comisd raises FE_INVALID on a quiet NaN). Reproduced with a small program (fork per case): with the base headers 164 of about 225 (operation, empty operand) pairs of a survey of the interface trapped in the SSE build. I confirmed the rest of the diagnosis: 1/[0,1] (SSE2 intervals only; the FPU build computes it without divide-by-zero), log([0,1]) and [1e308]*10 legitimately raise divide-by-zero and overflow, and the flag inexact is raised by almost every operation (the direction probe 1 + 2^-60, and the rounded results). The correction: is_empty() (gaol_interval.h, shared by the SSE and FPU builds, and the twin of gaol_intervalf.h) is now !std::islessequal(left(), right()), which emits ucomisd instead of comisd: same instruction count with clang-18 -O3, one vmovapd fewer with gcc 9.4 -O3, and no measurable difference in a micro-benchmark (throughput 0.634 vs 0.634-0.640 ns with g++, 0.511 vs 0.511-0.514 ns with clang++-18; dependent chain 4.63-4.69 vs 4.63-4.69 ns and 4.71-4.79 vs 4.71-4.79). I also had to make interval::emptyset() compare nothing (SSE: _mm_set1_pd(NaN) into the __m128d constructor; FPU: write lb_ and rb_ directly), because in a build without optimization it went through interval(double), whose test -oo < v && v < +oo compares the NaN and trapped by itself (sqrt and log of a negative interval died in Debug for this reason). The survey then drops to 38 trapping pairs (SSE) and 40 (FPU) from 164; the rest is deliberately left (see open_questions), as the orchestrator asked: the other operations are only documented. Documentation: a new section 'The floating-point exceptions' in doc/using.md and in manual/v5/gaol.tex (exceptions must be disabled while GAOL computes; which operations raise divide-by-zero, overflow, inexact, invalid; the flags tell nothing about the results; init() resets the environment before main(); the SSE2 operations of a GAOL_PRESERVE_ROUNDING build mask the exceptions again), a condition in doc/accuracy.md and in the accuracy chapter of the manual, a note on is_empty() in its Doxygen comment and in the manual, and the test described in doc/tests.md.

## Tests

New section in tests/rounding_direction.cpp (existing program, no build-file change), after the 'exceptions stay masked' paragraph. (1) On every platform, in process: for six empty sets (interval::emptyset(), interval(3,2), sqrt([-2,-1]), log([-2,-1]), [1,2]&[3,4], [3,4]&[1,2]), each made opaque to the compiler with gaol::rnd_keep, is_empty() is true and raises no exception flag (feclearexcept / fetestexcept(FE_ALL_EXCEPT) == 0); for three nonempty intervals ([1,2], [1], [-oo,+oo]) it is false and raises no flag; interval::emptyset() itself raises no flag. (2) Where glibc provides feenableexcept and fork (defined(__GLIBC__) && defined(_GNU_SOURCE) && defined(__unix__)): each of these is computed and told empty in a child process with FE_INVALID enabled (SIGFPE caught in the child to exit with a status of its own, so that ASan does not report it and no core file is written); a control child does 0.0/0.0 first, and if the processor does not trap (aarch64 without trap support, riscv, emulators, feenableexcept returning -1) the test prints that it skips that part. Non-glibc platforms (Windows, macOS, musl) run part (1) only and say part (2) is skipped. Before the fix: 12 checks fail with is_empty reverted, 5 with only emptyset() reverted in Debug.

## Behaviour change

is_empty() no longer raises FE_INVALID on the NaN bounds of an empty interval, so a program that enabled the invalid-operation exception is no longer killed by SIGFPE at each emptiness test of an empty interval, nor by the many operations that begin with it (+, -, *, /, %, sin, log, pow...); a program reading the flags no longer sees a spurious FE_INVALID after them. interval::emptyset() no longer compares a NaN in an unoptimized build (sqrt, log... of an out-of-domain interval, which return it, no longer trap there). Values of all results are unchanged. The exceptions of the other operations are unchanged (documented, see open_questions).

## API and ABI

none. is_empty() and interval::emptyset() are inline in the headers, with the same signatures; no exported symbol changes and no installed file is added. Code compiled against the old headers keeps the signaling comparison until it is recompiled.

## Risks

(1) MSVC and macOS are not testable here: the in-process check 'is_empty() raises no exception flag' runs on every platform and relies on std::islessequal being quiet, as C99/C++11 require; I did not verify the MSVC library (if its islessequal raised FE_INVALID on a NaN, the Windows jobs would show it, and no crash would follow). On arm64 with Clang the old comparison was already quiet, so the check is then vacuous there. (2) The trap part needs glibc; on aarch64, riscv64, s390x and ppc64le containers the control child (0.0/0.0 with FE_INVALID enabled) decides at run time whether the processor or the emulator traps, and the test prints 'The processor does not trap an invalid operation here ... skipped' otherwise; the child handler relies on sigaction, and a sanitizer that ignores user SIGFPE handlers would make the control report 'not trapped' and skip (harmless). (3) The child process uses fork(): fine for these single-threaded tests, also under ASan (verified); a core file is disabled with RLIMIT_CORE in the child. (4) The flags claims in doc/using.md (divide-by-zero for 1/[0,1] only with the SSE2 intervals, inexact from the probe 1 + 2^-60) were measured with GCC 9.4 on x86-64 in the SSE and FPU builds, not on other platforms, which is why the text says 'almost every' and 'where GAOL checks the rounding direction with an addition'. (5) The intervalf change was checked by compiling with GAOL_FLOAT_INTERVALS: the two float tests pass.

## Open questions and decisions for the maintainer

1. Operations that still raise FE_INVALID (trap) on the NaN bounds of an empty operand, in the survey with FE_INVALID enabled after the fix (SSE build; the FPU build adds unary minus, whose interval(-right(), -left()) compares a NaN): with the empty set as first operand: is_canonical, split, strictly_straddles_zero, set_contains(I), set_contains(double), set_disjoint, set_geq, sqrt, exp, min, max, floor, ceil, chi, sqrt_rel, operator<< (conversion to std::string), interval(NaN); as second operand: operator&= (x & empty: !(Ibd[0] >= bd[0]) in gaol_interval_sse.h, !(I.left() <= left()) in gaol_interval_fpu.h), set_disjoint, set_leq, min, max. Each is a signaling comparison or a call on a NaN bound before or without the emptiness test. Per the orchestrator I did not touch them; making them quiet is the same at-no-cost change (std::isgreaterequal in operator&=, is_empty() first in set_disjoint, set_contains, sqrt, exp, floor, ceil...) and would let the whole interface run trap-free on empty operands, which the maintainer may want as a new TODO point (x &= f(x) with an empty f(x) is the common case in contractors). 2. GAOL_PRESERVE_ROUNDING with the SSE2 intervals: GAOL_RND_ENTER_SSE() calls round_upward_sse(), which writes MXCSR with GAOL_SSE_MASK | _MM_ROUND_UP, that is with every exception masked and the SSE flags cleared, and GAOL_RND_LEAVE_SSE() restores only the rounding bits: the operations +, -, *, /, sqr(), inverse()... mask again the exceptions the program had enabled (verified: MXCSR masks 0x1d80 before, 0x1f80 after; 1/[0,1] no longer traps with FE_DIVBYZERO enabled). That is an environment leak of the kind of point 27 (rounding direction that does not leak): the preserve build should change only the rounding bits, as its leave macro does. I documented the current behaviour in doc/using.md and the manual rather than change it. 3. gaol::init() called for the first time (before main()) does fesetenv(FE_DFL_ENV), which resets the enabled exceptions and the flags: documented; a program enabling exceptions in a static constructor that runs before GAOL's initialization loses them. 4. intervalf::is_empty() (developer-only) got the same one-line change for consistency, compiled and tested with -DGAOL_FLOAT_INTERVALS=1; drop that hunk if the maintainer wants the float intervals left as they are. 5. interval(double l, double r) and interval(double) still compare their arguments with signaling comparisons (l <= r, -oo < v && v < +oo): only reached with a NaN supplied by the program (interval(NaN), interval(NaN, x)), where trapping is arguably right; not changed.

## For doc/differences.md

- **`is_empty()` and `interval::emptyset()` raise no floating-point exception.** The empty set has NaN bounds, and `is_empty()` compared them with `<=`, a signaling comparison: with the invalid-operation exception enabled (`feenableexcept(FE_INVALID)`) every emptiness test of an empty interval, and every operation that starts with it, died on SIGFPE, and without it the test raised `FE_INVALID`. `interval::emptyset()` did the same in a build without optimization, through the comparisons of `interval(double)`. `is_empty()` now uses `std::islessequal` (`ucomisd` for `comisd`, same cost) and `emptyset()` sets its bounds without comparing. The other operations still raise the exceptions they raise (divide-by-zero for `log([0, 1])`, overflow for `[1e308]*10`, inexact for almost every operation): the exceptions have to be masked while GAOL computes (`doc/using.md`, the manual); `tests/rounding_direction.cpp` checks the empty sets with FE_INVALID enabled, in a child process (glibc).

## Reviews

### 24-correctness-0: changes

Blocking:
- The new 'The floating-point exceptions' text (doc/using.md, third bullet and the paragraph before 'The flags tell nothing...'; the same text in manual/v5/gaol.tex, section sec:fp-exceptions) is incomplete about FE_INVALID, the exception programs enable most often. It says invalid-operation comes from the empty set and lists only divide-by-zero, overflow and inexact otherwise. I measured invalid raised, and trapped under feenableexcept(FE_INVALID), on nonempty operands. (1) SSE2 build: interval::operator*= raises it for a zero bound times an infinite bound. interval(0.0)*interval(1.0, +oo) dies with SIGFPE in operator*=. The flags survey shows it for every pair of a [0], [0,+oo] or [-oo,0] operand with an infinite-bound operand. The FPU build does not raise it there. (2) pow, in both builds: CORE-MATH's gaol_cr_pow raises invalid for a subnormal exponent (cr_pow(2, 4.9e-324) and cr_pow(2, 1e-310) both set it), so pow(interval(1,2), interval(4.9e-324)) traps. In the SSE build pow([1],[1,+oo]) also traps, inside operator*=. Because the text puts invalid on the empty set only, a reader can conclude that after this fix FE_INVALID may stay enabled while GAOL computes on nonempty operands, and would be killed by [0]*[1,+oo] or pow. The author's open_questions and ledger_todo repeat the same suggestion, that quiet comparisons would let the interface run trap-free.
- The claim 'GAOL's initialization, which runs before main(), sets the default environment (fesetenv(FE_DFL_ENV)), which masks every exception; a program enables them in main() or later, not in a static object initialized before GAOL' is false with GAOL_PRESERVE_ROUNDING. In gaol/gaol_common.cpp, init() calls fesetenv(FE_DFL_ENV) only inside #if !GAOL_PRESERVE_ROUNDING. I checked with a constructor(101) that calls feenableexcept(FE_INVALID). In the default SSE build fegetexcept() is 0 at main() (reset). In a GAOL_PRESERVE_ROUNDING build it is 1 and MXCSR mask 0x1f00 (nothing reset). The same paragraph already treats GAOL_PRESERVE_ROUNDING for the other claim, so it should here too.

Non-blocking remarks:
- doc/using.md and manual: 'after an operation of GAOL, fetestexcept(FE_INEXACT) is raised whatever the result' is too strong. Measured with no inexact flag: unary minus, abs, floor, &, |, is_empty() and emptyset() (SSE and FPU builds). The bullet above says 'almost every operation'. Say 'after almost every operation'.
- doc/using.md and manual: the GAOL_PRESERVE_ROUNDING list of operations that mask the exceptions again ('+, -, *, /, sqr() and inverse()') is short. I measured MXCSR mask 0x1f00 -> 0x1f80 also after operator% and div_rel. pow(x, n), sqrt, exp, sin, mid, abs, hypot, atan2, fma and cancel_minus left it unchanged. Add % and div_rel, or say 'in particular'.
- gaol/gaol_interval.h, comment above the rounding functions (about line 1018): 'is_empty() reads it as !(left() <= right())' is now stale, since the code is !std::islessequal(left(), right()). Update the wording.
- doc/accuracy.md: the reflow leaves a very short line ('hold on every architecture and with'). Re-wrap the paragraph.
- gaol/gaol_intervalf.h hunk (twin fix for the developer-only float intervals): correct and it compiles with GAOL_FLOAT_INTERVALS, but the intervals of floats are otherwise not touched by this point. The author already offers to drop it.
- MSVC and macOS are untestable here. The in-process 'raises no exception flag' check relies on std::islessequal being quiet. It cannot false-fail on a platform whose comparison is quiet, and it would report a platform whose islessequal raised the flag. Fine as is, worth watching in the Windows CI job.


### 24-correctness-1: approve

Non-blocking remarks:
- gaol/gaol_intervalf.h line 168: the header now uses std::islessequal without #include <cmath>, so it no longer compiles on its own. `#include "gaol/gaol_intervalf.h"` alone with -DGAOL_FLOAT_INTERVALS=1 gives "islessequal is not a member of std"; the base header compiled alone. All real TUs (gaol_intervalf.cpp, the tests) include <cmath> first, and the header is not installed, so nothing breaks. Add `#include <cmath>` next to <limits>, or drop the hunk (open question 4 of the report).
- doc/using.md ("after an operation of GAOL, fetestexcept(FE_INEXACT) is raised whatever the result") and the same sentence in manual/v5/gaol.tex section 3.3 overstate. Measured in the default SSE build: -X, abs, &, |, floor, max(X,Y) do not raise FE_INEXACT, and sqrt(empty) raises only FE_INVALID.
