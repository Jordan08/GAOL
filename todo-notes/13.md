# Point 13: a point interval is written in a form the reader refuses

Report of the agent that made the change (written in English, as produced), and the reviews. The branch is `todo-13-point-interval-text`; head at the time: `38d4f20`.

## Commits

- eb92122 operator<< writes <a, a> for a point interval only where its digits are exact, else [a, b]
- 38d4f20 Docs: the bounds format writes a point interval [a, b] unless its digits are exact

## What was wrong and what the change does

In the format `bounds` (the default), display_bounds() wrote every point interval `<a, b>`, a and b being the texts of its double rounded downward and upward. The reader takes `<a, b>` only for two expressions that evaluate to the same double exactly: a decimal that is no double, such as 0.1, is read as the two doubles around it, so even `<0.1, 0.1>` is refused (as the manual says). `interval(0.1)`, written `<0.1, 0.1000000000000001>`, was therefore refused: `gaol::textToInterval` throws `input_format_error` and `gaol_ieee1788::textToInterval` gives the empty set, contrary to the manual. About 61 % of the 11 788 point-interval texts of the new test were refused (1/3, pi, 1e23, subnormals, DBL_MAX, all the negatives with 16 digits...). GAOL 4.2.3 already wrote the same text. display_bounds() now writes `<a, a>` only when `l == r` and the two texts are equal, which happens only when the text is the double itself (the lower text is at most the double, the upper one at least it), so the reader gets back the very point; otherwise it writes `[l, r]`, which the reader reads as an interval enclosing the point (`interval(0.1)` is `[0.1, 0.1000000000000001]`). One deviation from the condition given in the TODO: a zero of either sign keeps the angles (`|| l == 0.0`). `interval::zero()` and `x - x` are `[-0, +0]` (SSE2 and FPU builds), their texts `-0` and `0` differ as strings although the reader takes `<-0, 0>`, and with the plain `left == right` they would go from `<-0, 0>` to `[-0, 0]`, which is not the "angles when the bounds are equal" the manual describes. Tests are added to tests/numbers.cpp and tests/ieee1788.cpp, shown to fail without the fix. The manual, the Doxygen comment of `interval_format`, doc/tests.md and three example comments are corrected.

## Tests

The reference values are the exact decimal value of the written text against the double, and the double itself.

## Behaviour change

With the default format `bounds`, a point interval whose double the digits of interval::precision() do not write exactly is written `[a, b]` (the two bounds rounded outward) instead of `<a, b>`: `interval(0.1)` is `[0.1, 0.1000000000000001]`, `interval(1.0/3)` `[0.3333333333333333, 0.3333333333333334]`. That text is read back by textToInterval, gaol_ieee1788::textToInterval and operator>> as an interval enclosing the point, where the old `<a, b>` was refused (input_format_error, or the empty set with gaol_ieee1788::textToInterval), so `textToInterval(intervalToText(interval(0.1)))` is no longer the empty set. Points written exactly are unchanged (`<4, 4>`, `<0.5, 0.5>`, `<1e+22, 1e+22>`, `<0, 0>`, `<-0, 0>` for [-0, +0]). The format `agreeing`, which calls display_bounds() when the right bound is above 10 times the left one (so for every negative interval, and for intervals of very different magnitudes), follows; the formats width, center and hexa are unchanged. Examples 02 and 06 print `[a, b]` where they printed `<a, b>`. Programs that matched the old `<a, b>` text of inexact points break (IBEX and Codac not checked, as asked).

## Risks

(1) Text output changes for inexact points: user code matching `<a, b>` breaks. (2) `<a, a>` relies on bound_to_text() rounding exactly outward, so that two equal texts are the double itself; the tests check it on 11 788 texts (exact value compared with the double), but the hexfloat flag, where the C library writes the digits, is not covered. (3) The zero rule `l == 0.0` is a deliberate deviation from the TODO's `left == right`, documented in the code comment and pinned by a test; a maintainer who prefers the plain rule changes one condition and the test `... of zero: in angles`. (4) An earlier draft of the test expected the text of `2.0/3.0` evaluated at run time, which depends on the rounding direction (upward once GAOL is initialized); it now uses hexadecimal literals, and the texts compared have no exponent (the exponent width of some C runtimes is not relied on). (5) The other platforms of the CI were not run; the change of the library is a string comparison, and the tests parse the texts with GAOL's own reader and the exact-value helpers of the suite.

## Open questions and decisions for the maintainer

1. Decision (made, to confirm): a zero of either sign keeps the angles (`<-0, 0>` for interval::zero() and x - x with SSE2). The alternative is the plain `left == right` of the TODO, which writes `[-0, 0]` for them (the tests show only the zero test fails under it), simpler but it changes the display of the most common point interval and the outputs `<0, 0>` shown in the manual for computed zeros. 2. For point 16: `<a, a>` is GAOL's own syntax, not an interval literal of IEEE 1788-2015 (Table 9.5 and 12.11.5: a point interval is `[m]`); 13.3 asks intervalToText for a literal of 12.11 and a value of cs that restricts the output to the portable syntax. When point 16 makes intervalToText write the bounds format, it should probably write `[a, a]` (or `[a]`) rather than `<a, a>`. 3. The TODO's diagnosis is right, with one precision: the empty set is what gaol_ieee1788::textToInterval gives; gaol::textToInterval throws input_format_error. The defect is older than v5 (GAOL 4.2.3 wrote `<l, r>` with the C library rounding, and refused it). 4. Other formats for a point interval: hexa writes `[a, a]` bit for bit and reads back exactly (tested); width and center write `out << l` under upward rounding, so `interval(0.1)` is `0.1000000000000001`, which does not enclose the double and reads back [0x1.99999999999ap-4, 0x1.99999999999a1p-4] (point 16, documented as display formats); agreeing writes `0.100000000000000~[0, 1]` for 0.1, which the reader refuses (by design, the manual says only bounds and hexa read back) and goes through display_bounds() for negative points, which are fixed. 5. Bug noticed, not fixed: in tests/input_output.cpp, test_input(), the `try` catches input_format_error and prints it (`catch (...) { std::cerr << e; }`), and the line `<-inf,-inf>` throws (as manual/v5/gaol.tex line 1344 says: `inf` reads as [dmax, +oo], so the two bounds differ) where the test expects [-oo, -dmax]; the assertions after it (`[-inf, -inf]`, `[-inf]`, `inf`, `[inf]`, `[inf,inf]`, `<inf,inf>`) never run. The try/catch should go and the two `<inf,...>` cases be corrected or removed. 6. Bug noticed, not fixed: in the agreeing format, `I.right() > 10*I.left()` is true for every negative interval, so negative intervals are always written by the bounds format, never with agreeing digits. 7. Decimal texts under a stream with a comma locale (`[1,5, 2,5]`) are still refused by the reader (review n° 21, point 16), so the manual's "the text read back encloses the interval written" holds for streams with the C locale; the new tests use the classic locale. 8. examples/examples.md lines to mark fixed in the bookkeeping: see `docs`.

## For doc/differences.md

- **A point interval is written in a form the reader takes.** In the format `bounds` (and in `agreeing` where it writes the bounds), `operator<<` writes `<a, a>` only for a point interval whose double the digits write exactly (`<4, 4>`, `<0.5, 0.5>`, `<-0, 0>`), and `[a, b]`, the two bounds rounded outward, otherwise.
  - **Before.** Every point interval was written `<a, b>`, the text of its double rounded downward and upward: `interval(0.1)` was `<0.1, 0.1000000000000001>`. The reader takes `<a, b>` for two numbers that are the same double, exactly, so it refused the text (`input_format_error`, and the empty set with `gaol_ieee1788::textToInterval`): `textToInterval(intervalToText(interval(0.1)))` was the empty set, against the manual, and so was every point whose double has more digits than `interval::precision()` (GAOL 4 wrote the same).
  - **Now.** `interval(0.1)` is `[0.1, 0.1000000000000001]`, which is read back as an interval containing it; a zero of either sign keeps its angles, `<-0, 0>` being read as `[-0, 0]`. `tests/numbers.cpp` reads back the text of point intervals written with 1 to 25 digits and six sets of flags, and `tests/ieee1788.cpp` checks `textToInterval(intervalToText(interval(0.1)))`.

## Reviews

### 13-correctness-0: approve

Non-blocking remarks:
- The report says interval::zero() is [-0, +0] in both the SSE2 and FPU builds. In the FPU build it is [0, 0] and prints `<0, 0>`; x - x is [-0, 0] in both. The code and test comments correctly say 'with the SSE2 intervals', so only the report is imprecise.
- The `l == 0.0` deviation from the TODO's plain `left == right` is sound and documented, but it is a decision for the maintainer. The plain rule would print `[-0, 0]` for interval::zero() and x - x, and `<-0, 0>` is what the manual outputs (`<0, 0>`) and the old behaviour show.
- gaol/gaol_interval.h: the `hexa` item still says 'same as bounds except that bounds are printed in the hexadecimal-significand form'. hexa writes a point as `[a, a]` and bounds may now write `<a, a>`. This was already inexact before the change and belongs to point 16.
- examples/05_interval_newton.cpp line 307: the comment says 'a point interval that the digits write exactly as <a, b>'. `<a, a>` would match the other comments and the manual.
- examples/02_decimals_and_rump.cpp: interval(0.1) now prints as `[0.10000000000000000555, 0.10000000000000000556]` under a label saying 'a point'. The label explains it, but the text no longer shows that it is a point. Optional wording.
- tests/numbers.cpp: the four new round_trip(...) calls in hexadecimal_output (0.1, -1/3, smallest, MAX) exercise the hexa format, which this change does not touch, so they do not pin the new behaviour. They are harmless extra coverage.
