   `width_and_center_output()`, and `main()` calls all of them. Point 13 is
   already in configure-clean, and the merged tree agrees with it:
   - `display_bounds()` still has point 13's rule for `<a, a>` (exact digits
     or a zero), plus the `angles` argument of point 16.
   - `bound_to_text()` writes a zero bound to nearest (704f478).
   - Point 13's tests are there: `expect_point_output` in numbers.cpp, and the
     `intervalToText(interval(0.1))` read-back in ieee1788.cpp.

   The sse build and the full ctest pass right after the merge: 49 of 49,
   with intervalf and interval2f skipped.
   The merge also brings in the pragma for GCC 12 on aarch64 at the top of
   tests/numbers.cpp. The branch's last CI run (122e0f0) failed only on
   "Debian 12 Bookworm arm64": `numbers` stopped with `std::invalid_argument:
   stol`, which is the GCC 12 miscompilation that this pragma works around.

2. **The center format calls `midpoint()` alone.** It used to call
   `mid_rad()` and throw away the radius. Now only the width format calls
   `mid_rad()`. The text written is the same.

3. **`gaol_ieee1788::intervalToText` is in the operations checked by
   `tests/rounding_direction.cpp`.** It is now a library function that uses
   `GAOL_RND_ENTER`/`LEAVE`. The entry writes `x` and `interval(0.1)`, so it
   covers the empty set, the bounded operands and a point.

4. **Named locals for the random intervals of `width_and_center_output()`.**
   The two random doubles of each interval are now drawn one at a time. This
   alone did not make the population the same on every compiler, and I
   measured why: `Random::any()` and `Random::operator()(emin, emax)` in
   `tests/gaol_tests.h` call `make(bits() & 1u, bits() % 2047u)`. The order
   of those two `bits()` calls is unspecified. A probe that hashes 1000 draws
   gave `1a010532c6acecd7` with GCC and `b9710532c6acecd7` with Clang 18.
   Both functions now draw the exponent, then the sign, into named locals.
   That is the order GCC used, so the populations GCC tested on every platform
   stay the same (the hash is still `1a010532c6acecd7`), and Clang now draws
   the same doubles. In the width test, the uniform pair is also drawn in
   GCC's former order.
   Result: gaol_test_numbers runs 390607 checks with both GCC and Clang, and
   the per-check counts are identical (`diff` is empty). Before the change,
   the merged tree ran 390607 checks with GCC and 390103 with Clang.

5. **The center is checked to half a unit of its last digit.** This is
   sound: the center is written by the C library with the direction set to
   nearest. A correctly rounded conversion is then at most half a unit away,
   and the bound is inclusive, so a tie passes whichever way it is broken.
   - The old unit of the general format was |x|·10^(1−p), which is 1 to 10
     real units of the last digit. `unit_of()` now reads the real unit from
     the text:
     - fixed format: 10^−p;
     - scientific format: 10^(e−p);
     - general format: 10^(e+1−p);

     where e is the power of ten of the first nonzero digit written.
   - The radius check ("rad() rounded upward, less than one unit of its last
     digit") uses the same helper, so it is now held to one real unit as well.
     That is what `bound_to_text()` guarantees: it rounds to nearest, then
     moves by one unit.
   - Why the half unit is portable: the previous CI run on this branch passed
     Windows (MSVC, MinGW-w64 12 to 15, MSYS2 UCRT64/CLANG64), macOS and every
     container. At 20 digits the old check already failed for any C library
     that is not exact past 17 digits, such as the old msvcrt.dll printf. So
     the conversions on the CI are exact, and exact conversions to nearest are
     within half a unit.

6. **Manual.** I added one sentence after "the radius rounded upward" in the
   width item: at the default 16 digits, [0.1, 0.3] is written
   `0.2 (+/- 0.1000000000000001)`. The radius is the double nearest to 0.1,
   which is a little above 0.1, and this is intended. I checked the output by
   running a program against the library. The manual has no
   [3.452, 3.453] example (that one is in tests/input_output.cpp), so the
   sentence goes after the text on the rounding of the radius, next to the
   [4, 5] example.

# Point 13 decision: [a]

The maintainer decided on point 13: "operator<< devrait lui aussi abandonner
<a, a> au profit de [a]." This section reports how this branch implements it.
Head after this work: `24b048e`. Nothing pushed.

## Commits

- `65c2b58` operator<< and intervalToText write a point interval [a], and a zero [0], instead of <a, a>
- `24b048e` Docs: a point interval is written [a]; the reader still takes the <a, a> of GAOL 4

## What was wrong and what the change does

`display_bounds()` (gaol/gaol_interval.cpp), which the bounds format of
`operator<<`, the agreeing format (for negative intervals) and
`gaol_ieee1788::intervalToText` call, wrote a point interval `<a, a>` when
`l == r` and the texts of its two bounds were equal, or when it was a zero of
either sign. `<a, b>` is GAOL's own syntax, not an interval literal of IEEE
1788-2015, where a point is `[m]` (12.11). On this branch intervalToText
already avoided it (an `angles` argument), writing `[4, 4]`.

Now `display_bounds()` has one rule for both functions:

- a point interval whose two texts are equal (so the text is the double
  itself: the lower text is at most the double, the upper one at least it) is
  written `[a]`: `[4]`, `[0.5]`, `[-1024]`, `[1e+22]`;
- a point interval of zero, `[-0, +0]`, `[+0, +0]` or `[-0, -0]` (and
  `[+0, -0]`), is written `[0]`, the text of +0 with the flags of the stream
  (`[+0]` under showpos, `[0.000]` in fixed with 3 digits);
- every other interval, including a point whose texts differ, keeps `[l, r]`:
  `interval(0.1)` is `[0.1, 0.1000000000000001]`.

The `angles` argument is gone, so `display_bounds()` has again the signature
it has on configure-clean (an internal function, hidden visibility).

**The bounds are compared by their bits**, not with `l == r` and `l == 0.0`.
Under denormals-are-zero (a program linked with -Ofast, or code that sets
MXCSR), a subnormal compares equal to 0. A first version with `l == 0.0 &&
r == 0.0` wrote `[0, 5e-324]`, `[5e-324]`, `[-5e-324, 0]` and even
`[21, 22] * 5e-324` as `[0]` under DAZ, silently (probe in
`scratchpad/tmp/16/probe/daz.cpp`). The old code wrote them in angles
(`<0, 4.940656458412465e-324>`), which the reader refused. With the bits, at
16 digits, they are written `[0, 4.940656458412465e-324]`,
`[4.940656458412465e-324]`, `[-4.940656458412465e-324, 0]`, and read back as
intervals enclosing them. A test pins it (below).
intervalToText writes `[4]` and `[0]`, still with 16 digits, a decimal point,
the classic locale, whatever the format, the precision and the locale.

**Zero: `[0]` for all four, not `[-0]` for `[-0, -0]`.** I checked what the
reader gives: `"[0]"` reads as `[+0, +0]`, `"[-0]"` as `[-0, -0]`. Both are
the set {0}, so either choice reads back to the same set; the choice is not a
matter of soundness. I chose `[0]` for every zero point because:

1. one set, one text: the text of `interval::zero()` is now the same on every
   build (it is `[-0, +0]` with the SSE2 intervals and `[+0, +0]` with the FPU
   ones; before, `<-0, 0>` and `<0, 0>`), and so is the text of `x - x`,
   `-interval(0.0)` and `interval(-0.0)` (both `[-0, -0]`);
2. the number of a literal `[m]` is a real number (12.11), and -0 and +0 are
   the same real;
3. bit-for-bit recovery is the hexa format's job (`[-0x0p+0, 0x0p+0]`), and
   `[-0]` could not give it for `[-0, +0]` anyway;
4. the signs of zero bounds stay visible where they matter as bounds:
   `[-0, 1]` is still written `[-0, 1]` (the decision of point 10 not to
   normalize zeros is about operations, and is untouched).

The alternative (`[-0]` when both bounds are -0, `[0]` otherwise) is a
one-line change; the tests would need their "without a sign" check relaxed.

**The reader still takes `<a, b>`** (no change to the parser). New test: the
texts `<4, 4>`, `<0.5, 0.5>`, `<-1024, -1024>`, `<-0, 0>`, `<0, 0>`,
`<1e+22, 1e+22>` are read back as the point. `"<0.1, 0.1>"` is still refused
(existing tests).

**Soundness of `[a]`.** `<a, a>` checked itself when read: an inexact `a` made
the reader refuse the text. `[a]` does not: the reader takes the hull of `a`.
So "equal texts imply the text is the double" is now load-bearing. It holds:
for a finite nonzero bound, `bound_to_text()` compares the text with the
double exactly and moves the last digit outward if needed, whatever the C
library does (but not under denormals-are-zero for a subnormal: see Risks); a zero is written exactly; with the hexfloat flags the C++
library writes `%a` without precision (the standard says so for
`floatfield == fixed | scientific`; libstdc++, libc++ and the MSVC STL do it),
which is exact. The tests check, for every `[a]` written (4573 texts), that
`a` is exactly the double, with the exact rational arithmetic of the tests.

## Behaviour change

- operator<< in the bounds format (and in the agreeing format for negative
  intervals): a point interval whose digits are exact is written `[a]`
  (`[4]`, `[-2]`, `[0.5]`) instead of `<a, a>`; a zero point of either sign is

## Risks

- Text output changes for every exact point interval and every zero point:
  user code or scripts that match `<a, a>` break, and so does code that splits
  every interval text on ", ".
- `[a]` is not self-checking when read (see Soundness above): a C++ library
  that wrote a hexfloat with a limited precision and ignored the rounding
  direction would make `[a]` inexact. The standard forbids the precision for
  hexfloat; the decimal paths do not depend on the C library.
- **Denormals-are-zero, low precision (not fixed, not mine).**
  `bound_to_text()` tests `x == 0.0`, `x > 0.0` and `x < 0.0`, which DAZ
  makes true or false for a subnormal: it then writes a subnormal bound to
  nearest, not outward. At 16 digits the error is below one subnormal step for
  the small subnormals, and the texts read back enclose (tested). At 1 digit
  they do not: `[22u]` (u = 5e-324) is written `[1e-322]`, read as
  `[20u, 21u]`; `[21u, 22u]` is written `[1e-322, 1e-322]`. The angles of the
  old code made the reader refuse those texts (a loud failure); `[a]` and
  `[l, r]` are read silently. The fix is in `bound_to_text()`: test the bits
  (`(bits << 1) == 0`, `std::signbit`) instead of comparing with 0.0. It is
  point 11's open remark and point 4's domain, so I left it; it is a few
  lines if the maintainer wants it on this branch.
- The all-digits test writes 309 to 1080 digits; it checks at run time that
  the platform's library writes them exactly and skips each case otherwise
  (with a message). CI platforms (MSVC, musl, macOS) not run here.

## What was wrong and what the change does

**B1, decimal comma (fixed).** Under a locale with a decimal comma,
`operator<<` writes the stream's decimal point. With that locale, the
one-number literal `[a]` became two numbers, and the reader (whose decimal
point is always `.`) accepted them without any error:

- `[-2,5]` for `interval(-2.5)` was read as [-2, 5];
- `[12,5]` was read as the empty set;
- `[0,]` (a zero in the fixed format with showpoint and precision 0) was read
  as [0, +oo];
- `-denorm_min` in fixed with 1074 digits was read as [-0, +oo].

The fix is in `display_bounds()`, which now writes `[a]` only when the text
has no comma. Otherwise it writes the two bounds, as for any other interval:
`[-2,5, -2,5]`, `[0,000, 0,000]`, `[0,, 0,]`, `[4,, 4,]`. The reader refuses
all of these, just as it refuses every bound written with a decimal comma. I
checked this with the probe `tmp/16/probe/comma2.cpp`, against the reader:
every text that the probe writes under `fr_FR.utf8` is either refused or read
back as an interval containing the point. That covers 12 points in 6 settings
(general 16 digits, fixed|showpoint 0, fixed 3, scientific|showpoint 0,
fixed 1074, hexfloat), and also `std::string(I)` under the global locale.
The zero path uses the same guard.

I chose to test the text (`left.find(',')`) rather than the numpunct decimal
point, for two reasons:

- `interval(4)` stays `[4]` under the comma locale, where there is nothing to
  confuse;
- any comma is caught, whatever produced it.

`intervalToText` is unaffected: it always uses the classic locale.

**B2, DAZ test on macOS x86_64 (fixed by a run-time guard).**
`subnormal_output()` now writes each bound of its seven intervals with a
default stream, at 16 digits and to nearest (`RoundingToNearest`), once under
DAZ and once without it. This is what `bound_to_text()` does when it hands
such a bound to the C library under DAZ. If any pair of texts differs, the
test prints, for example, "The C library writes 0 under denormals-are-zero,
and 4.940656458412465e-324 without it: the output of subnormals with the
mode is not checked", and returns. It covers gdtoa (FreeBSD, macOS) and
whatever the UCRT does. On glibc the texts are equal, so the 7 checks still
run. The root cause, `x == 0.0` in `bound_to_text()`, is point 4/11 and is
not fixed here (see the open questions).

**B3, `doc/accuracy.md` (fixed).** The `intervalToText` row now says:
