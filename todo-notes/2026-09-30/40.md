### (d) GAOL_NODISCARD before C++17

`e4ce618` makes the macro `__attribute__((warn_unused_result))` for GCC and Clang before C++17, and `_Check_return_` of `<sal.h>` for Visual C++. I checked the choices with GCC 13.3, clang-18 and MinGW-w64 GCC 13.

**What each attribute does**

- **GCC and Clang.** `-Wunused-result` is on by default, and GCC and Clang warn for a function call and for an operator call alike. There is one difference: GCC also warns about `(void)f()` with the GNU attribute, and with `[[gnu::warn_unused_result]]` too; Clang does not. The doc says so.
- **Clang and `[[nodiscard]]` before C++17.** Clang warns about the extension under `-pedantic` (`-Wc++17-attribute-extensions`), as the old comment said.
- **Visual C++.** `_Check_return_` expands to nothing outside `/analyze`. Under the code analysis it gives warning C6031. The doc now says "only the code analysis reports it (C6031)". I could not test this here: there is no Visual C++ on the machine.
- **Clang for Windows** (clang-cl) defines `__clang__` and takes the GNU attribute.

**It compiles in C++11, 14, 17 and 20, and adds no warning**

I compiled `tests/nodiscard.cpp` with GCC 13 and clang-18, in C++11, 14, 17 and 20. The flags were those of the build plus `-Wall -Wextra -pedantic -Werror=attributes -Werror=unused-result`.

- The program that uses every result compiles in all 16 cases.
- With `GAOL_DISCARD`, the compilation fails with exactly one "ignoring return value" error.
- The other warnings are the same with and without the attribute (`-DGAOL_NODISCARD=`): 30 `-Wunused-parameter` plus 3 `-Wdeprecated-copy` with GCC, and 31 plus 1 with Clang. They are old and come from GAOL's headers.
- i686 MinGW-w64 GCC 13 behaves the same in C++11, 14 and 17. x86_64 MinGW-w64 11 is refused by `gaol_config.h` (point 6).

**The attribute lands on every declaration that uses the macro**

- I counted the `WarnUnusedResultAttr` nodes in clang-18's AST (`-Xclang -ast-dump`), minus the count with `-DGAOL_NODISCARD=`. The result is 317 declarations in C++11, 14, 17 and 20 alike.
- The full builds (GAOL itself is in C++11, so it now gets the GNU attribute) give no warning.
- The macro can only add warnings. It never changes code generation or the ABI: the attribute is not part of the mangled name.

**What I fixed in the tests**

Under `ctest -j`, a refused test and a nodiscard test could therefore run two `cmake --build` at once in the same build directory, which the comment meant to prevent. Both now take `gaol_compile_tests`.
2. **An attribute the compiler ignores went unnoticed.** Two misplacements were tried in C++17 (details under "How the test was shown to fail"):

   The tests now add `-Werror=attributes`.
3. **The include directories.** They were `CMAKE_BINARY_DIR` and `CMAKE_SOURCE_DIR`, which are wrong when GAOL is a subproject with `WITH_TESTS` on. They are now `PROJECT_BINARY_DIR` and `PROJECT_SOURCE_DIR`. Point 5's tests have the same defect, which I did not fix (see open question 4).
4. **Docs.** The comment and `doc/using.md` said "C++11 and C++14, which are the standards of GCC before 11 and Clang before 16". In fact C++14 is the default of GCC 6 to 10, of Clang 6 to 15 and of Visual C++. The warning C6031 is now named.

### (e) Outputs of the manual

I wrote a runner (`$SCR/tmp/40/run_examples.py`). It:

- extracts the 88 example blocks of `manual/v5/gaol.tex` that show an output;
- compiles each against a build, with `using namespace gaol`, or `gaol_ieee1788` for the two blocks of that chapter;
- runs it and compares what it prints with what the manual shows.

**Boolean outputs.** On the base (`origin/configure-clean`), 58 of 88 blocks matched. 29 of the mismatches were bool outputs printed 1/0 instead of true/false: the review's "three examples" was an undercount. The 30th was `chi(interval::emptyset())`, which prints `-nan` where the manual shows `nan`. `f7a98d3` adds `boolalpha` to exactly those 29 blocks, and they all match now.

**chi() of the empty set.** `f7a98d3` did not fix the -nan: it added a note saying that the program prints -nan, so the manual still contradicted the program. The cause is in the library:

- `width()`, `mig()`, `smig()` and the radius of `mid_rad()` all return `GAOL_NAN` (0x7ff8…, positive) for the empty set.
- `chi()` instead divided the NaN bounds, so the sign was whatever the generated code left:
  - GCC, SSE2 and FPU: 0xfff8…, which prints `-nan`;
  - clang-18: a positive NaN.
- It also raised FE_INVALID through `fabs(NaN) <= fabs(NaN)`.

`chi()` now returns `GAOL_NAN` for an empty interval (`f477f2c`). As a result:

- it prints `nan` with every compiler, as the manual shows;
- it no longer raises FE_INVALID (checked with `fetestexcept`: 0 in the SSE and FPU builds).

The note and the sentence about NaN in the introduction are removed. The manual's `chi` entry gains one sentence: NaN for the empty set, 1 for [-oo,+oo], 0 for the other intervals with an infinite bound.

With the fix, all 88 blocks match in the SSE, FPU and Clang builds, in C++11 and C++17. The one exception is the output `@version` of `gaol::version`, which is the manual's macro for 5.0.0.

### B1 (blocking): Visual C++ honours [[nodiscard]] in C++14. Fixed, with a correction

The reviewer is right that the rewritten sentence was false for current Visual C++. But the fix it suggests, `_MSC_VER >= 1920`, would break Visual Studio 2019 16.0. This is what Visual C++ does with `[[nodiscard]]` in `/std:c++14` (`nd1.cpp`):

| Visual C++ | `[[nodiscard]]` in C++14 | `__has_cpp_attribute(nodiscard)` in C++14 |
|---|---|---|
| 2015 (19.0) | accepted silently, no warning | not defined |
| 2017 15.0 (19.10) | error C2429, "requires compiler flag '/std:c++latest'" | not defined |
| 2017 15.7 (19.14) | error C2429, "requires compiler flag '/std:c++17'" | not defined |
| 2019 16.0 (19.20) | error C2429, as 15.7 | 0 |
| 2019 16.1 to 16.3 (19.21-19.23) | warning C5051, "requires at least '/std:c++17'; ignored" | 0 |
| 2019 16.4 (19.24) to 2026 (19.51) | honoured: C4834 at level 1, on by default | 201603, then 201907 |

In the honoured versions, `(void)` and `static_cast<void>` silence C4834. In every version, `__has_cpp_attribute(nodiscard)` is 201603 or 201907 in `/std:c++17`.

Microsoft's documentation disagrees with itself here. The C4834 page says `/std:c++14` and later, while the attributes page says `/std:c++17` and later. What the compilers do settles it.

**The macro (`gaol/gaol_config.h`)**

1. From C++17 on: `[[nodiscard]]`, unchanged.
2. Before C++17: `[[nodiscard]]` when all of these hold:
   - C++ (not C);
   - `__has_cpp_attribute` is defined;
   - not Clang;
   - `_MSC_VER` is undefined or at least 1924;
   - `__has_cpp_attribute(nodiscard)` is non-zero.
3. Otherwise: `__attribute__((warn_unused_result))` with GCC and Clang, `_Check_return_` with Visual C++ 2005 and later, and nothing elsewhere.

Why each condition:

- **`__has_cpp_attribute` inside a nested `#if`.** A preprocessor without it would read `0(nodiscard)`.
- **`_MSC_VER >= 1924` on top of `__has_cpp_attribute`.** Visual C++ 2017 15.8 and 15.9, the first with `__has_cpp_attribute` according to Microsoft, are not on Compiler Explorer. So I could not check what they report while they still refuse the attribute.
- **Checked on Compiler Explorer.** The macro expands to `[[nodiscard]]` in C++14 and gives C4834 with 16.4 (19.24) and later. With 2015, 2017 15.7, 2019 16.0 and 16.3 it expands to `_Check_return_`, that is to nothing outside `/analyze`, and compiles without any warning even under `/we5030 /we5051` (`cfg.cpp`). clang-cl 18 gets the GNU attribute in C++14 and `[[nodiscard]]` in C++17.
- **`_Check_return_`, now tested.** Under `/analyze`, Visual C++ 2019 16.0 and the latest version report C6031 for a thrown-away call of a function, a static member, a member and an operator. `(void)` silences it (`cr.cpp`). `/analyze` also gives C28251 where the definition lacks the annotation of its declaration, but only with code analysis on, in Visual C++ before 16.4.
